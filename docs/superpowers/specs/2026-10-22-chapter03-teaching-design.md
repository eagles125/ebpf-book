### 2.2 设计原则

- **bad/fixed 差异最小化**：每对只差一处语义错误，README 给「预期 verifier 日志关键行」+「为什么拒绝」+「修复原则」三段；把读者注意力钉在验证器推理本身。
- **「编译成功≠能加载」机械化**：verify-build 验收 bad 与 fixed **都编译通过**——bad 程序不是语法错误，clang 层面全部合法，拒绝发生在加载期。加载级行为（通过/拒绝的实际日志）本机不可实测，一律「预期输出示例 + 运行级待验证」标注。
- **教学映射**：画廊七对对应 tasks.md 六类常见错误 + ch02 预告的 probe 界限；01-pkt-parse 锚点让「验证通过」路径也有实物（正反两条路径都有代码可走）。
- **代码注释规范**（STYLE.md 实战模板规则 2）：bad/fixed 源码中文注释覆盖失败模式、verifier 拒绝原因、修复后的边界检查原因；锚点程序覆盖数据结构字段语义、边界检查原因、helper 选型原因、map 类型选型原因。
- **产物不入库**：`.gitignore` 追加 `book/examples/chapter-03/` 下的可执行物（锚点 loader 与练习可执行物；`vmlinux.h`/`*.skel.h`/`*.o` 已被全局规则覆盖）。
- **内核兼容**：预期日志与行为以 5.10+ 为基准（有界循环 5.3、`bpf_loop` 5.17 等演进点保守措辞并注明）；本机 7.0.0-38 仅作 BTF/编译口径参考，不作日志事实来源。

## 5. 验证策略（编译级）

`scripts/verify-build.sh`（单章版，模式同第 2 章）：

1. BTF 前置检查（`/sys/kernel/btf/vmlinux`）；
2. `01-pkt-parse`、画廊七对（bad 与 fixed 都必须 `make` 编译成功）、exercises 两目录逐个 `make`；
3. 汇总 `PASS/WARN/FAIL`，退出码 0=全绿；结果写入章级 README 验证状态说明区。

本机全部可执行（无网络依赖）；加载级（实际通过/拒绝的 verifier 日志）按约定标注「预期输出示例 / 运行级待验证」。

## 6. 技术风险与边界

| 风险 | 缓解 |
|------|------|
| verifier 日志文本随内核版本漂移 | 以 5.10+ 稳定格式与 verifier.rst 措辞为基准，正文标注「日志行随版本略有差异」，本机口径仅作参考 |
| `kernel/bpf/verifier.c` 万行级，全讲不现实 | 只讲概念结构（env/reg_state/探索-剪枝-边界三板斧），函数级细节标注「以所用内核源码为准」 |
| 与第 2 章内容重复（边界检查已讲过） | 分工明确：ch02 讲「怎么写对」，ch03 讲「内核怎么证明 + 被拒时怎么读日志」；回指不重复 |
| 7 对 bad/fixed 逐对讲解导致画廊节膨胀 | 每对固定四段式小结构（背景/日志关键行/为什么拒绝/修复原则），单对控制在 1.2–1.7k |

| 加载级行为本机不可实测 | 预期日志 + 「运行级待验证」标注，与全书约定一致 |
