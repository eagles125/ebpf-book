## 学习目标

读完本章后，你应当能够：

- 说出验证器（verifier）的三类安全保证——内核态内存安全、可终止、权限最小化——并在加载路径（`BPF_PROG_LOAD` → license 检查 → **verifier** → JIT）上指出验证发生在哪一步、拒绝时返回什么（一节 1.1/1.3）。
- 用过近似（over-approximation）一句话解释为什么「模拟执行」能替「真实执行」作保，并说明状态探索与剪枝为什么既安全又高效（二节 2.2/2.4）。
- 读懂 `bpf_reg_state` 指针状态族：给出一个寄存器类型（如 `PTR_TO_MAP_VALUE_OR_NULL`、`PTR_TO_PACKET_END`），说出它允许什么算术、要求什么检查（二节 2.3）。
- 讲清静态验证与运行时定界如何分工、保守性意味着什么——为什么合法程序也可能被拒，以及这为什么是代价而非缺陷（一节 1.2/1.4）。
- 独立跑通失败画廊七对的 bad/fixed 对照（`diff` 加 `make`），并说出每对被拒背后的安全理由（三节 3.1–3.7）。
- 逐行解读一条真实的验证器拒绝日志：定位出错指令、读懂寄存器状态行、把日志信号对回根因类别（四节实战）。
- 完成 2 项课后扩展任务：修复含三处组合错误的坏程序；按一条日志片段反推根因并写程序复现（课后扩展任务节）。

第 2 章多次把话头留给「第 3 章」：讲程序要素时说「编译成功≠能加载」，讲指令集时说「指令集越小，verifier 能证明的越多」，讲加载路径时说「这是第 3 章整章的主题」。本章兑现这些预告，并正面回答那个被反复预告的问题：一段 C 代码编译成字节码之后，内核凭什么敢把它放进自己的地址空间执行？

## 一、验证器的目标与安全模型

第 2 章 1.1 把 eBPF 程序定义为「经 verifier 验证的受限 C 子集」，但当时「验证」只交待了位置（加载路径第 2 步），没有交待内容。本节补上内容：验证器证明什么（1.1）、证明不了的交给谁（1.2）、验证发生在加载路径的哪一步（1.3）、以及证明的边界——不保证什么、为何会误伤合法程序（1.4）。本节纯讲解，动手现场在三节失败画廊与四节实战。

### 1.1 为什么内核不能直接执行任意 C

背景问题：内核态的一行越界写，破坏的是整个系统的内存；一个不停机的循环，挂住的是系统关键路径。要让外部代码进内核执行，只有两种选择：信任作者，或先证明再放行。内核模块选择了前者——代价是一个空指针就能让系统崩溃（第 1 章「eBPF 与内核模块的对比」有完整对照表）；eBPF 选择后者——用表达力换可证明性。程序类型（program type）、挂载点（attachment point）与上下文对象之所以都要在加载前申报清楚（第 2 章一节的八要素），正是为了给「证明」提供依据。

验证器对每份提交上来的字节码做出三类安全保证：

1. **内核态内存安全**：每一次访存（读或写）都可证明落在合法区域——上下文对象申报过的字段、映射值登记过的大小、512 字节栈内已初始化的槽位、或报文缓冲内经过界检查的偏移。指针不是「一个数字」：2.3 的寄存器状态族会给每个指针配上类型与边界。
2. **可终止**：执行步数有界。跳转目标必须落在程序内，循环必须可证明收敛，总执行指令数有预算上限（2.4/2.6）。eBPF 程序不是独立线程，跑在收包、系统调用这类内核关键路径上，「跑飞了再说」不在选项里。
3. **权限最小化**：程序只能调用辅助函数白名单（whitelist，按程序类型正向登记的能力面）内的能力；上下文按类型申报，越申报越访问不了；部分能力还要求 GPL 兼容 license（2.7）。

**教师视角**：把验证器想成「入境安检」——它不是不让进，而是只放行能证明自己行为有界的访客。你申报行程（程序类型、上下文、license），安检员把你未来每一步都推演一遍：任何一步说不清楚（越界？不停机？白名单外？），整份申请退回，附一份逐行的说明（verifier 日志）。两个高频误区：误区一，「verifier 是运行时检查器」——不对，它运行在加载时刻、程序第一次执行之前，对字节码做静态证明；程序运行时 verifier 已经不在路径上，这正是 eBPF 数据面零检查开销的来源（1.2 展开）。误区二，「被拒 = 程序有错」——多数拒绝是「安全不可证明」而不是「不安全」，1.4 展开这个区别。

常见失败点：三类保证各对应一类典型拒绝——内存安全类（未判空的映射值、越界的报文读、标量当指针解引用）见三节 3.1/3.2/3.7；可终止类（上界取自输入的循环）见 3.5；权限类（白名单外的辅助函数）见 3.6。

### 1.2 静态验证与运行时定界的分工

背景问题：有些安全性在加载期根本无法证明。数组映射的下标来自运行时计算，是否越界要看当时的值；报文有多长要看当时的包。验证器不能「等值出来再说」——那它怎么处理这些证明不了的部分？

答案是两层防线分工。第一层是**静态证明**：验证器在加载期证明类型、边界与终止性，加载时一次付费、运行期零开销——能证明的绝不留给运行时。第二层是**运行时定界**：证明不了的交给运行时机制兜底。第 2 章 3.2 给过一个标准样本：数组映射对越界下标的查找不报错，而是**在辅助函数内部定界、返回 NULL**——「下标是否越界」在加载期不可证明，内核把它下沉到辅助函数内部裁决，调用方拿到的要么是 NULL 要么是合法指针，随后的义务是判空（第 2 章 5.2 的 `if (!p)`；判空后 verifier 凭什么证明使用安全，类型学机制在 2.3 展开）。

成本权衡是理解分工的钥匙。静态证明把成本压在加载期：每次加载验一遍，之后每包每事件都不再付检查费——这是热路径（收包、高频事件）承受得起 eBPF 的根本原因。运行时定界则每次执行都付费：辅助函数内部的判断、程序里显式写的边界检查，都落在数据面上。内核的设计取向由此清楚：**能静态证明的绝不下沉到运行时**。上下文字段访问是极端样本——程序类型登记过布局，固定偏移的读取在加载期静态放行，零运行时成本（预告⑦之一，2.3 作答）；数组映射越界是另一端——值依赖运行时输入，静态不可证明，下沉到辅助函数内定界。

值得停下来想的问题：报文边界为什么不学数组映射，也交给运行时兜底？做得到，但两种兜底形态各有代价：要么允许程序读到越界内存、再靠异常兜住——内核态不可接受；要么在每条访存前偷偷插入检查——每包付费，还把错误从加载期推迟到运行期。内核选择了第三种：把边界做成**显式契约**——程序写出 `data + 大小 > data_end` 一类的检查，验证器核对并据此放行后续访存（2.5 讲验证器怎么读懂这个契约）。错误在加载期暴露，运行期零额外开销。三节 3.2 的画廊对（缺一行检查即被拒）就是这个契约的反面教材。

### 1.3 验证发生在哪一步

第 2 章 4.3 给过加载路径的四步，本节把「验证」放回现场：

```text
bpf(BPF_PROG_LOAD)                     —— 第 2 章 4.3 的四步
  ├─ 1. license 等属性检查              （license 与 GPL 专用辅助函数的匹配精确到每次调用，2.7）
  ├─ 2. verifier 静态验证   ← 本节与二节   拒绝：返回 -EACCES，日志经 log_buf 带回用户态
  ├─ 3. JIT 编译                        （第 6 章）
  └─ 4. 组装程序对象，返回 fd
```

拒绝路径值得单独记：验证不通过时，`bpf(BPF_PROG_LOAD)` 返回 `-EACCES`，同时把验证日志写入加载参数指定的日志缓冲（log_buf）——libbpf 通常把它打到 stderr。日志怎么拿、详细度怎么调，机制在 2.7，实操在四节实战。与它最容易混淆的是 `-EPERM`：权限不足（非 root 且 `unprivileged_bpf_disabled=2`）时程序**没进验证**就失败。两者的判别是排错第一步——`-EPERM` 查权限档位，`-EACCES` 读验证日志（预告⑧在此回收；判别流程排错节收口）。验证通过后才轮到 JIT（Just-In-Time，即时编译）编译与挂载（第 6 章）。

「编译成功≠能加载」在此正式展开（预告①）。编译器回答的问题是「这是不是一份合法的 C 程序、合法的字节码」——语法、类型、ABI（应用程序二进制接口）；验证器回答的是「这份字节码未来在**所有可能输入**下是否安全」——内存、终止、权限。两个问题互不覆盖：编译通过对安全性几乎没有发言权，验证器也不关心代码风格。三节画廊的七个 bad 程序全部 clang 编译通过、全部在加载期被拒——第 2 章反复预告的「两件事」，在本章被做成可以亲手 diff 的实验。最后回扣第 2 章 1.8 的生命周期六步：那六步里的「验证」一格，展开后就是本章全部内容。

### 1.4 安全模型的边界

背景问题：通过验证，等于程序正确吗？不等于。验证器证明的是「**这一版程序**在**这类输入**下**安全**」——每次访存有界、必然停机、只调白名单内的能力。三个限定词各有边界：

- 「安全」不含逻辑正确：统计口径写错、规则写反、该丢弃的包放行了——只要访存合法，验证器一律放行。逻辑正确性永远在开发者这边。
- 「这一版」是字节码级：改一行、重新编译，就要重新验证；证明结论不跟源码走，跟字节码走。
- 「安全」不含数据质量：多 CPU 写竞争导致计数偏少（第 2 章 3.4）、LRU 满表静默淘汰旧表项（第 2 章 3.3）——验证器完全不管这类「安全但不对」。

保守性取舍是安全模型最重要的边界。验证器的回答只有两种：「可证明安全」与「无法证明」，后者一律拒绝——哪怕程序实际安全。代价清单里最刺眼的一条：**合法程序也可能被拒**。三节画廊正是这份代价清单的实物化：未判空的查找（3.1）、缺边界检查的报文读（3.2）、对尾界指针的算术（3.3）、分支外读未初始化栈变量（3.4）、上界取自输入的循环（3.5）、白名单外的辅助函数（3.6）、把标量当指针解引用（3.7）。这七类写法在 C 语言里都「合法」，clang 都放行——被拒的理由全部是「安全不可证明」。保守换来一个极有价值的性质：**拒绝即安全**——内核不需要为「没证明到的区域」再准备运行时兜底，1.2 的两层防线由此闭合。

**学生动手**：进入三节之前，先把自己的直觉当一次被检对象。写下你预想中「合法但难证明」的三种 C 写法（找不着方向的话，从这三处想：上界来自输入的循环、值在运行时才确定的数组下标、编译器可能优化掉的检查）。学完三节后回来对答案：你的三种写法分别对应画廊哪一对？如果有一条三节没覆盖，说明你找到了画廊之外的类别——带着它去读所用内核的 `Documentation/bpf/verifier.rst`，权威性远超任何教程。

检查点（先自答，再看提示）：

1. 验证器的三类安全保证分别挡住什么？各举一个会被该类检查拒绝的写法。（提示：内存安全——不判空就解引用映射值指针；可终止——上界取自报文的循环；权限最小化——调用本程序类型白名单外的辅助函数；现场分别见三节 3.1/3.2/3.5/3.6。）
2. 数组映射越界下标的查找，为什么不能靠验证器在加载期证明？它由哪层防线兜底、程序侧还剩什么义务？（提示：下标值运行时才知道，静态证明无从谈起；辅助函数内部定界返回 NULL——1.2 的运行时定界；程序侧义务是判空。）
3. `bpf()` 返回 `-EPERM` 与 `-EACCES`，分别说明加载路径走到了哪里？排错第一步为什么先分这两者？（提示：`-EPERM` 没进验证——查权限档位；`-EACCES` 进了验证没通过——读日志；两个方向混着查会浪费时间。）

## 二、验证流水线内核实现分析

一节回答了「验证器做什么」，本节回答「它怎么做」：进入 `kernel/bpf/verifier.c`，沿一次验证的真实顺序拆开流水线——入口与两个核心结构（2.1）、指令级模拟执行的抽象解释原理（2.2）、寄存器状态族（2.3）、控制流探索与剪枝（2.4）、边界推导（2.5）、栈模型与终止性（2.6）、辅助函数约束与日志（2.7）。本节纯讲解，不含加载与挂载操作；凡随内核版本演进的函数名、结构体字段，一律保守措辞并注明「以所用内核源码为准」（讲解以 5.10+ 稳定行为为基准，本机内核 7.0 仅作口径参考）。

### 2.1 验证入口与总体管线

背景问题：一节说的「三类保证」在代码里从哪个函数开始？答案：`kernel/bpf/syscall.c` 的程序加载路径在 license 等属性核对之后，调用 `kernel/bpf/verifier.c` 的 `bpf_check()`——验证的总入口（函数名与调用点以所用内核源码为准；预告⑥的「逐指令模拟执行」从这里开始兑现）。

`bpf_check()` 内部的骨架大致是：先做指令级预处理（指令清洗、死代码消除一类，随版本演进），再做控制流图（Control Flow Graph，CFG）检查（跳转落点、回边合法性——2.6 终止性的第一道），然后进入逐指令状态探索主循环（2.2/2.4 的全部内容），通过后做收尾修正（重定位、偏移回填一类）交还加载路径。

理解这条管线，只需要两个核心结构（都声明在 `include/linux/bpf_verifier.h`，字段随版本演进，以所用内核源码为准）：

- **`bpf_verifier_env`**：验证环境——一次验证会话的全部上下文。待验证程序的指针、日志缓冲（`bpf_verifier_log` 一族，2.7）、能力档位标志（特权与否直接改变严格度，2.6/2.7 会两次遇到它）、探索工作栈与当前状态。verifier 的几乎每个函数都以 env 为第一参数——「一次会话」就是这个结构。
- **`bpf_verifier_state`**：探索中的机器状态——某一时刻程序「可能处于」的状态：全部寄存器各自的 `bpf_reg_state`（2.3）加上调用栈帧。探索主循环的基本动作只有一句话：取一条指令，在当前 state 上推演它对 state 的改变。

管线整体形状：

```text
bpf_check()（kernel/bpf/verifier.c）
  ├─ 预处理：指令清洗、死代码消除一类（随版本演进）
  ├─ CFG 检查：跳转落点必须落在程序内；回边按能力档裁决（2.6）
  ├─ 逐指令状态探索主循环（2.2/2.4）
  │    ├─ 每条指令：按寄存器状态族推演效果（2.3）
  │    ├─ 分支：两条路径各自探索；等价状态剪枝（2.4）
  │    └─ 访存裁决：边界推导放行/拒绝（2.5）
  └─ 通过：交还加载路径做 JIT；拒绝：-EACCES + 日志（1.3）
```

### 2.2 指令级模拟执行

背景问题：不真正执行程序，怎么知道它安全？答案是抽象解释（abstract interpretation）：用「所有可能取值的集合」代替「具体值」来执行程序。真实执行时，寄存器里是一个 64 位数；模拟执行时，「寄存器」里是一段**描述**——类型（标量还是什么指针）、取值范围（上下界）、偏移与对齐。这套描述的载体就是 2.3 的 `bpf_reg_state`。

三类对象的抽象取值域各不相同。寄存器的抽象值 = 类型 + 范围（「标量，范围 [0, 15]」或「报文指针，偏移 [0, 14]」这样的形状）；栈槽是寄存器的溢出位，同一套抽象（2.6 讲栈特有的初始化跟踪）；映射值不像寄存器那样被逐值全程跟踪——它以「定型」为主：是否已判空、大小是否登记（2.3 的映射值类型学）。

为什么「模拟」就能保证「真实执行」安全？这是全书到这里最值得想透的一段论证，关键词是过近似：模拟推演的从来不是某一次输入下的行为，而是**所有可能输入的合取**——抽象值始终是具体值的超集。打个沙盘推演的比方：推演时把敌人可能出现的一切位置都摆上棋子；推演里每一步你都赢（每次访存都合法、每条路径都收敛），实战就不可能输——任何一次真实执行都只是推演的一个特例。反过来，「推演赢不了」不代表「实战会出事」：推演输掉只说明「证明不出来」，这正是 1.4 保守性的来源。

两个推论贯穿二节余下的所有小节：其一，验证器对「具体值」天然失明——凡取决于输入的值都进入范围追踪而不是数值追踪（2.5 的全部内容）；其二，模拟必须覆盖所有路径——多条路径、状态合并与剪枝因此不可避免（2.4）。还有第 2 章 2.1 的那个前提在此兑现（预告④）：这套推演之所以可行，是因为指令集足够小、每条指令语义可枚举——「指令集越小，verifier 能证明的越多」在流水线层面的含义就是：主循环里每种操作码都对应一条有限的推演规则。

### 2.3 寄存器状态族 bpf_reg_state

背景问题：抽象值长什么样？答案集中在 `struct bpf_reg_state`（声明于 `include/linux/bpf_verifier.h`，字段随版本演进）的三块信息里：**类型**（`type` 字段，枚举 `bpf_reg_type`）、**范围**（有符号/无符号上下界一族，外加位级三元抽象 tnum——每一位取「确定 0 / 确定 1 / 未知」，命名随版本演进）、**指针信息**（偏移与定界信息一族）。其中类型是安全模型的主角——一节的三类保证，落到寄存器层面就是一张类型表。5.10+ 稳定核心集如下（枚举成员随内核版本增删，以所用内核源码为准）：

| 类型 | 语义 | 允许的算术 | 要求的检查 |
|---|---|---|---|
| `SCALAR_VALUE` | 纯数值，不指向任何内存 | 任意算术与位运算 | 不可解引用 |
| `PTR_TO_CTX` | 上下文对象指针（按程序类型申报） | 不做自由算术，字段按固定偏移访问 | 访问落在申报的上下文布局内 |
| `CONST_PTR_TO_MAP` | 映射本体指针 | 不可算术、不可解引用 | 主要作为查找类辅助函数的映射参数 |
| `PTR_TO_MAP_KEY` | 映射键指针 | 偏移算术（受限） | 只读，偏移在 key 大小内 |
| `PTR_TO_MAP_VALUE_OR_NULL` | 查找返回：值指针**或** NULL | 不可算术、不可解引用 | 必须判空；判空后收窄为下一行 |
| `PTR_TO_MAP_VALUE` | 已判空的映射值指针 | 偏移算术，越出 value 边界即拒 | 访存偏移落在 value 大小内 |
| `PTR_TO_STACK` | 栈帧指针（r10 派生） | 偏移算术 | 偏移在 512 字节栈内且槽已初始化（2.6） |
| `PTR_TO_PACKET` | 报文数据指针（`data` 派生） | 偏移算术（受界约束） | 先与 `PTR_TO_PACKET_END` 建立关系才可解引用（2.5） |
| `PTR_TO_PACKET_END` | 报文尾界（`data_end`） | **不可算术** | 只参与比较 |
| `PTR_TO_BTF_ID` | 内核结构体指针（按 BTF 类型申报） | 按申报类型的字段偏移 | 访问落在申报类型的布局内 |
| `PTR_TO_MEM` | probe 系辅助函数读入的登记缓冲 | 按登记大小 | 访存落在登记大小内 |
| `NOT_INIT` | 尚未赋值的寄存器 | 不可使用 | 使用即拒（与 2.6 栈未初始化同源） |

读这张表的钥匙在最后两列的分工：「允许的算术」回答类型可否派生新指针，「要求的检查」回答程序要补交哪些证明才能从「弱定型」升级成「强定型」。两个最常用的例子：查找返回的 `PTR_TO_MAP_VALUE_OR_NULL` 必须判空，`if (!v) return ...;` 之后空路径退出、非空路径上类型收窄为 `PTR_TO_MAP_VALUE`——三节 3.1 的 bad 就是没有这一步；`PTR_TO_PACKET_END` 只许比较、不许算术——三节 3.3 的 bad 对它做了加法，日志 `R2 pointer arithmetic on pkt_end PROHIBITED` 一类（预期输出示例 / 运行级待验证；日志行随内核版本略有差异）。

预告⑦之一在此正式作答。第 2 章 5.2 问过：为什么敢直接读 `ctx->next_pid`？任意内核指针为什么必须走 probe 系辅助函数？用这张表回答：ctx 以 `PTR_TO_CTX` 进入程序；程序类型登记时，内核已通过每个类型自己的上下文访问校验回调（`is_valid_access` 一类，随版本演进）向验证器申报了「哪些偏移、什么宽度、读还是写」——对固定偏移的字段读，加载期即可证明落在申报范围内，静态放行、零运行时开销。而把 ctx 里读出的标量（`SCALAR_VALUE`）强转成指针再解引用，在类型学上直接不成立——`SCALAR_VALUE` 不可解引用（三节 3.7 的 `invalid mem access 'scalar'`）。真正的任意内核地址必须经 probe 系辅助函数：由辅助函数在内部定界，把「内核空间任意地址」收窄成 `PTR_TO_MEM` 的登记缓冲。一句话总结：内核不按「地址」管理访问，按「类型 + 申报」管理访问。

### 2.4 控制流探索与状态合并

背景问题：程序有分支，每个分支之后寄存器状态不同——模拟怎么不漏掉任何一条路径？分两步：先建图，再探索。

第一步，CFG 检查：把程序看成有向图（指令是节点，跳转是边），验证「跳转目标必须落在程序内」「回边按能力档裁决」（2.6）。这一步只看图的结构，不看数据。

第二步，从入口开始逐指令探索。遇到条件跳转，验证器把「跳转不成立」的那条路径连同它的状态压入待探索栈（`push_stack` 一类函数，随版本演进），沿当前路径继续；当前路径走完（退出、或被拒绝）后弹出下一条待探索路径继续。两条路各模拟一遍——不是抽一条代表，是全覆盖。

那「汇合点」呢？概念上，抽象解释在汇合点做保守合并——取两条路径中更宽的口径。Linux 验证器的实现没有显式的合并点：它逐路径探索到底，把「合并」的角色交给**状态等价判断**——新路径推进到某条指令时，若当前状态与这条指令上已经探索过的某状态等价（`regsafe` 一族比较函数，随版本演进），且新状态不比旧状态更宽，则后续执行必然已被覆盖，整段直接跳过。这就是状态剪枝（state pruning），`is_state_visited()` 一类函数是它的家。

状态爆炸（state explosion）为什么没有发生？理论上路径数随分支数指数增长，但剪枝把「等价状态」的后续探索合并掉了；再配两条硬预算：总执行指令预算（百万条量级，随版本调整——日志尾行 `processed N insns (limit ...)` 里的 limit 就是它）与每指令状态数、调用栈深度等上限。预算用尽即拒绝加载——「过于复杂」本身也算证明失败，呼应 1.1 的可终止保证。

一句定位精度追踪（precision tracking）：等价判断口径过宽会把不该剪的剪掉（漏掉真错误），验证器在「边界推导依赖某个标量的精确值」时临时收紧等价口径、必要时退回精确探索——机制随版本演进，本节记住「剪枝是保守的、必要时可回退」即可。

本节的探索树与剪枝标记的图形版，见「可视化：验证器状态探索与剪枝」一节的图 1——那里用一个双分支小程序把「两条路各模拟一遍、等价即剪」画成图。

### 2.5 边界推导

背景问题：范围从哪来？沿指令传播——常量装载给出确定值；运算按语义收窄或放宽；值不确定时给最宽范围。三组机制，各配一个本章后面会用到的例子。

**标量范围跟踪**。每个标量同时带着有符号/无符号两套上下界（字段随版本演进）与 2.3 提到的位级抽象。例（三节 3.5 的伏笔）：`n = *(__u32 *)data & 0xF`——按位与沿位级抽象传播：结果的低 4 位确定、其余位为零，无符号上界从 2^32−1 一步塌缩到 15（取值域收窄为 [0, 15] 共 16 个可能值）。以 `i < n` 为条件的循环因此可证明至多迭代 15 次——「上界变常数」是掩码指令的直接推论，不是验证器对循环网开一面。掩码位数按业务语义选，上界 = 2^位数 − 1（画廊 3.5 fixed 版注释同口径）。

**报文指针比较建立关系**（三节 3.2 的伏笔）。`data` 与 `data_end` 从上下文读出时，是两个**毫无关系**的指针：一个 `PTR_TO_PACKET`、一个 `PTR_TO_PACKET_END`。一句 `if ((void *)(eth + 1) > data_end) return XDP_PASS;` 之后，「不返回」那条路径上多了一条事实：报文指针的偏移加对象大小，不超过尾界的偏移——**比较建立了两指针的相对关系**，此后的解引用才可证明落在报文内。没有这句比较，关系不存在，第一次越界读即被拒（日志 `R2 offset is outside of the packet` 一类）。锚点程序 `book/examples/chapter-03/01-pkt-parse/pkt_parse.bpf.c` 每层协议头一行检查，正是这个机制的三连用——「通过路径」长什么样，本节是它的原理页。

**有符号/无符号与掩码修正**（练习 2 的伏笔）。两套界混用会产生「负偏移」：一个可能为负的值被当作偏移加到指针上，验证器拒绝并给出形如 `R2 min value is negative, either use unsigned or 'var &= const'` 的信号（预期输出示例 / 运行级待验证；日志行随内核版本略有差异）。处理方向两条：改用无符号语义让界对齐，或用掩码把取值域收窄到非负。本章练习 2 就是从这条日志反推根因——把本节机制读成排错能力。

### 2.6 栈模型与终止性

**栈模型**。BPF 栈固定 512 字节（第 2 章 2.1 埋的线头）。验证器对这 512 字节做**栈槽初始化跟踪**：每个槽位只有在「当前这条路径上先写过」之后才允许读；读到从未写过的槽即拒，日志两种形态——针对未初始化寄存器的 `R2 !read_ok` 一类，或按栈槽指认的 `invalid read from stack off ...` 一类（预期输出示例 / 运行级待验证；日志行随内核版本略有差异）。拒绝的理由是安全而不是洁癖：内核栈在使用之间不清零，未初始化的槽里可能残留前一次系统调用留下的进程敏感数据，读出并回传用户态就是一次信息泄露。三节 3.4 的 bad（分支外读未初始化栈变量）就是这条规则的现场。

严格度随特权档位变化——这是栈模型里必须点亮的一层：未初始化栈读的拒绝有配置前提。特权加载（`CAP_PERFMON` 一类能力档）下，验证环境里 `allow_uninit_stack` 一类档位标志置位（字段声明于 `include/linux/bpf_verifier.h`，在 `bpf_check()` 中按能力档赋值——以所用内核源码为准），未初始化栈读被放行：内核认为特权用户本就能读到这类数据，泄露模型对特权档不成立。同一份字节码，允许非特权 BPF 的配置拒绝、特权配置放行——**验证器的严格度随特权档位变化**不是缺陷而是信任模型的一部分；教学与代码审计一律按「必须初始化」对待（画廊 3.4 README 的特权豁免说明同口径）。

**终止性**（预告⑤回收）。第 2 章 2.3 的规则「跳转偏移必须落在程序内、程序必须可证明会终止」在流水线里是两道机制。第一道在 CFG 检查（2.4 第一步）：跳转目标越出程序边界即拒；回边（构成循环的跳转）是否放行，由能力档条件裁决——源码中体现为 `loop_ok` 与 `bpf_capable` 一类条件的组合（以所用内核源码为准）。第二道在状态探索：对放行的回边，验证器不数迭代次数，而是看探索是否收敛——循环体每转一圈，若状态落入已见过的等价状态（或不再变化），探索终止、证明成立；若始终无法收敛，拒绝，日志 `infinite loop detected at insn ...` 一类——这是特权路径的主形态；非特权路径上回边在 CFG 一层就被拒，日志 `back-edge from insn ... to ...` 一类。

版本演进一句话（保守措辞，以所用内核源码与文档为准）：5.3 之前，任何回边一律拒绝——「可证明会终止」靠禁止循环语法实现；5.3 起对特权程序允许有界循环（bounded loop）——语法放开，终止性改由「状态探索是否收敛」裁决。第 2 章那条规则前后两种实现口径，结论不变：无界执行进不来。再加上 2.4 的指令预算兜底，栈限 512 字节、指令预算百万级、循环必须收敛——三者共同把「无界」排除在模型之外。

### 2.7 辅助函数约束、白名单与日志

背景问题：权限最小化（1.1 第三类保证）怎么落地？两个机制：按程序类型登记的白名单，与按参数原型的类型检查。

**白名单按程序类型登记**。每个程序类型在内核里登记一组验证器操作（`bpf_verifier_ops` 一类结构，定义于 `include/linux/filter.h` 一类头文件，字段随版本演进），其中「给定编号，返回该类型的原型或 NULL」一类回调回答了「这个程序类型能否调用编号 N 的辅助函数」——可用面按类型裁剪：XDP 程序调不了 tracing 类的 `bpf_get_current_pid_tgid()`，反之亦然。这是第 2 章 1.3「每个程序类型只能看到自己可用的那部分辅助函数」的机制版（预告②在此回收机制，现场在三节 3.6；预告⑦的辅助函数侧面——probe 系能力的登记——也在此收口）。白名单落空的日志形态：`unknown func bpf_get_current_pid_tgid#14` 一类（预期输出示例 / 运行级待验证；日志行随内核版本略有差异）——注意措辞是「unknown func」而不是「不允许」：白名单按类型正向登记，miss 的含义是「此类型的世界里没有这个函数」。license 在同一层在场：部分原型标记为仅 GPL 兼容 license 可用，不兼容同样拒绝——第 2 章 4.3 第 1 步的回声。

**参数原型与类型检查**。每个可用的辅助函数都有原型（`bpf_func_proto` 一类结构，字段随版本演进）：登记返回值类型与每个参数的类型约束（`ARG_PTR_TO_MAP_KEY`、`ARG_CONST_MAP_PTR`、`ARG_PTR_TO_CTX` 一族）。调用点逐一核对：实参寄存器的当前类型（2.3 表）必须匹配参数约束，常量约束（如缓冲大小须为编译期常量）同样在此核对。这是 2.3 类型学的消费端——那张表「要求的检查」列里，一半义务来自这里的原型。例：`bpf_map_lookup_elem` 的映射参数要求映射本体指针（对应 2.3 的 `CONST_PTR_TO_MAP`）、键参数要求指向键的指针（`ARG_PTR_TO_MAP_KEY`）——把标量传进去即拒；返回值定型为 `PTR_TO_MAP_VALUE_OR_NULL`，判空后才可解引用（1.2/2.3 的闭环）。

**日志如何产生与详细度控制**。验证过程中，逐条日志由 `verbose()` 一类函数写入挂在 `bpf_verifier_env` 上的日志缓冲（2.1 的 env）；每行的典型形态是「指令号 + 执行后的寄存器状态」——2.2/2.3 的推演过程原样落盘，失败时最后一行就是结论。详细度由加载参数的 log_level 档位控制：0 只给结论、1 给逐指令轨迹、2 追加更细的状态信息（档位语义随版本略有差异，以所用内核源码与 UAPI 注释为准）；缓冲区过小则日志被截断。怎么把日志拿到手、`bpftool prog load` 的日志开关、逐行读法——是四节实战的正题，那里把本节机制变成工作流。

**教师视角**：本节的讲解顺序是先类型（2.3）、再流程（2.4）、最后边界与栈（2.5/2.6）——这不是随意编排，而是与验证器的检查顺序同构：**先定性，再定量**。类型不对，一切免谈（`unknown func`、`invalid mem access 'scalar'`）；类型对了，才轮到「这个偏移在不在界内」。读者读日志的排查顺序也应该同构：先认类型错、再查边界错——把 2.3 的表当字典用，把 2.5 的机制当算术用。两个误区：其一，把白名单理解成「黑名单的补集」——它是按程序类型正向登记的能力面，「查无此函数」与「有此函数但不许用」根因不同，修复方向也不同；其二，把日志当报错文本背——日志行随内核版本漂移，值得记的是「信号 → 根因类别」的映射（排错节的速查表干的就是这件事）。

**学生动手**：在本机内核源码或文档中定位 `bpf_reg_state` 的定义，逐项核对 2.3 的表。本机装了内核源码的话，从 `grep -rn "struct bpf_reg_state" /usr/src/` 入手；没有源码就在文档站点按你的内核版本检索 `include/linux/bpf_verifier.h`。核对时盯三处：枚举成员的增删（2.3 表尾注）、范围字段一族（有符号/无符号上下界）的命名、指针偏移与位级抽象的拆分方式。把与 2.3 表不一致的条目记下来——「表会随版本漂移，并且你核对过当前版本」这件事本身，就是本章要教给你的能力。无源码环境的替代路径：读所用内核的 `Documentation/bpf/verifier.rst`，与 2.2/2.4 的机制对照。

检查点（先自答，再看提示）：

1. 同一个 XDP 程序调用 `bpf_get_current_pid_tgid()`，编译期与加载期各发生什么？日志大致长什么样？（提示：编译期不报错——原型都在头文件里，clang 不做白名单检查（第 2 章 1.3）；加载期白名单落空，日志 `unknown func ...#<id>` 一类——白名单按程序类型正向登记。）
2. `PTR_TO_MAP_VALUE_OR_NULL` 与 `PTR_TO_MAP_VALUE` 的差别是什么？哪一个可以直接解引用？（提示：前者是查找返回的「值或 NULL」联合定型，必须判空收窄成后者；直接解引用前者，就是三节 3.1 的 `invalid mem access 'map_value_or_null'`。）
3. 为什么「模拟执行」敢替「真实执行」作保？一句话说出过近似的方向。（提示：抽象值始终是具体值的超集——推演覆盖所有可能输入；推演中每步合法，真实执行作为特例不可能不合法。）
4. 512 字节栈限、百万条指令预算、循环必须收敛——三者共同把什么排除在模型之外？（提示：「无界」；这是 1.1 可终止保证的三道预算化机制——2.4/2.6。）
