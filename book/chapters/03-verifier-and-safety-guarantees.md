## 学习目标

读完本章后，你应当能够：

- 说出验证器（verifier）的三类安全保证——内核态内存安全、可终止、权限最小化——并在加载路径（`BPF_PROG_LOAD` → license 检查 → **verifier** → JIT（即时编译））上指出验证发生在哪一步、拒绝时返回什么（一节 1.1/1.3）。
- 用过近似（over-approximation）一句话解释为什么「模拟执行」能替「真实执行」作保，并说明状态探索与剪枝为什么既安全又高效（二节 2.2/2.4）。
- 读懂 `bpf_reg_state` 指针状态族：给出一个寄存器类型（如 `PTR_TO_MAP_VALUE_OR_NULL`、`PTR_TO_PACKET_END`），说出它允许什么算术、要求什么检查（二节 2.3）。
- 讲清静态验证与运行时定界如何分工、保守性意味着什么——为什么合法程序也可能被拒，以及这为什么是代价而非缺陷（一节 1.2/1.4）。
- 独立跑通失败画廊七对的 bad/fixed 对照（`diff` 加 `make`），并说出每对被拒背后的安全理由（三节 3.1–3.7）。
- 逐行解读一条真实的验证器拒绝日志：定位出错指令、读懂寄存器状态行、把日志信号对回根因类别（四节实战）。
- 完成 2 项课后扩展任务：修复含三处组合错误的坏程序；按一条日志片段反推根因并写程序复现（课后扩展任务节）。

## 一、验证器的目标与安全模型

第 2 章 1.1 把 eBPF 程序定义为「经 verifier 验证的受限 C 子集」，但当时「验证」只交待了位置（加载路径第 2 步），没有交待内容。本节补上内容：验证器证明什么（1.1）、证明不了的交给谁（1.2）、验证发生在哪一步（1.3）、证明的边界——不保证什么、为何误伤合法程序（1.4）。本节纯讲解，动手现场在三节失败画廊与四节实战。

### 1.1 为什么内核不能直接执行任意 C

背景问题：内核态一行越界写破坏整个系统的内存，一个不停机的循环挂住系统关键路径。要让外部代码进内核执行，只有两种选择：信任作者，或先证明再放行。内核模块选前者——代价是一个空指针就能让系统崩溃（第 1 章「eBPF 与内核模块的对比」有完整对照表）；eBPF 选后者——用表达力换可证明性。程序类型（program type）、挂载点（attachment point）与上下文对象都要在加载前申报清楚（第 2 章一节的八要素）——给「证明」提供依据。

验证器对每份提交的字节码做出三类安全保证：

1. **内核态内存安全**：每一次访存（读或写）都可证明落在合法区域——上下文申报过的字段、映射值登记过的大小、512 字节栈内已初始化的槽位、或报文缓冲内经过界检查的偏移。指针不是「一个数字」：2.3 的寄存器状态族为每个指针配上类型与边界。
2. **可终止**：执行步数有界。跳转目标必须落在程序内，循环必须可证明收敛，总执行指令数有预算上限（2.4/2.6）。eBPF 程序不是独立线程，跑在收包、系统调用这类关键路径上，「跑飞了再说」不在选项里。
3. **权限最小化**：程序只能调用辅助函数白名单（whitelist，按程序类型正向登记的能力面）内的能力；上下文按类型申报，越出申报范围的偏移即访问不了；部分能力还要求 GPL 兼容 license（2.7）。

**教师视角**：把验证器想成「入境安检」——不是不让进，只放行能证明自己行为有界的访客。你申报行程（程序类型、上下文、license），安检员把你未来每一步都推演一遍：任何一步说不清（越界？不停机？白名单外？），整份申请退回，附逐行说明（verifier 日志）。两个高频误区：其一，「verifier 是运行时检查器」——不对，它运行在加载时刻、程序第一次执行之前，对字节码做静态证明；程序运行时 verifier 已不在路径上，这正是 eBPF 数据面零检查开销的来源（1.2）。其二，「被拒 = 程序有错」——多数拒绝是「安全不可证明」而非「不安全」（1.4）。

常见失败点：三类保证各对应一类典型拒绝——内存安全类（未判空的映射值、越界的报文读、标量当指针解引用）见 3.1/3.2/3.7；可终止类（上界取自输入的循环）见 3.5；权限类（白名单外的辅助函数）见 3.6。

### 1.2 静态验证与运行时定界的分工

背景问题：有些安全性在加载期根本无法证明——数组映射的下标来自运行时计算，是否越界要看当时的值；报文有多长要看当时的包。验证器不能「等值出来再说」，这些证明不了的部分交给谁？

答案是两层防线分工。第一层**静态证明**：验证器在加载期证明类型、边界与终止性，加载时一次付费、运行期零开销——能证明的绝不留给运行时。第二层**运行时定界**：证明不了的交给运行时兜底。第 2 章 3.2 给过标准样本：数组映射对越界下标的查找不报错，而是**在辅助函数内部定界、返回 NULL**——「下标是否越界」加载期不可证明，内核把它下沉到辅助函数内裁决，调用方拿到的非 NULL 即合法指针。随之产生程序侧硬性义务：map_value_or_null（值或 NULL）型指针解引用前必须判空——这是 verifier 类型系统的定型要求，不是风格（判空后收窄成合法值指针，机制在 2.3 展开；第 2 章 3.2「NULL 检查义务」即此口径）。第 2 章 5.2 那处具体的 `if (!p)` 则需调停：在「数组映射界内 key 运行期不会返回 NULL」的前提下，它另兼诊断分类作用，属防御式写法、非 verifier 硬性要求——类型义务管所有「值或 NULL」指针，防御式判空是明知不为 NULL 的冗余，两层各自成立。

成本权衡是分工的钥匙。静态证明把成本压在加载期：每次加载验一遍，此后每包每事件不再付检查费——这是热路径（收包、高频事件）承受得起 eBPF 的根本原因；运行时定界则每次执行都付费——辅助函数内部的判断与显式边界检查都落在数据面上。设计取向由此清楚：**能静态证明的绝不下沉到运行时**。上下文字段访问是极端样本——程序类型登记过布局，固定偏移读取加载期静态放行、零运行时成本（预告⑦之一，2.3 作答）；数组映射越界是另一端——值依赖运行时输入，静态不可证明，下沉到辅助函数内定界。

值得停下来想：报文边界为什么不学数组映射，也交给运行时兜底？做得到，但两种兜底各有代价：要么允许程序读到越界内存、再靠异常兜住——内核态不可接受；要么每条访存前偷偷插检查——每包付费，还把错误从加载期推迟到运行期。内核选第三种：把边界做成**显式契约**——程序写出 `data + 大小 > data_end` 一类检查，验证器核对并据此放行后续访存（2.5 讲它怎么读懂这个契约）。错误在加载期暴露，运行期零额外开销。三节 3.2 的画廊对就是它的反面教材。

### 1.3 验证发生在哪一步

第 2 章 4.3 给过加载路径的四步，本节把「验证」放回现场：

```text
bpf(BPF_PROG_LOAD)              —— 第 2 章 4.3 的四步
  ├─ 1. license 等属性检查      （license 与 GPL 专用辅助函数的匹配精确到每次调用，2.7）
  ├─ 2. verifier 静态验证  ← 本节与二节  拒绝：返回 -EACCES，日志经 log_buf 带回用户态
  ├─ 3. JIT 编译                （第 6 章）
  └─ 4. 组装程序对象，返回 fd
```

拒绝路径值得单独记：验证不通过时 `bpf(BPF_PROG_LOAD)` 返回 `-EACCES`，验证日志写入加载参数指定的日志缓冲（log_buf）——libbpf 通常打到 stderr。日志怎么拿、详细度怎么调：机制在 2.7，实操在四节实战。最易混淆的是 `-EPERM`：权限不足（非 root 且 `unprivileged_bpf_disabled=2`）时程序**没进验证**就失败。判别是排错第一步——`-EPERM` 查权限档位，`-EACCES` 读验证日志（预告⑧在此回收；判别流程排错节收口）。验证通过后才轮到 JIT（Just-In-Time，即时编译）与挂载（第 6 章）。

「编译成功≠能加载」在此正式展开（预告①）。编译器回答「这是不是一份合法的 C 程序、合法的字节码」——语法、类型、ABI（应用程序二进制接口）；验证器回答「这份字节码未来在**所有可能输入**下是否安全」——内存、终止、权限。两个问题互不覆盖：编译不对安全性发言，验证器也不关心代码风格。三节画廊的七个 bad 程序全部 clang 编译通过、全部在加载期被拒——第 2 章预告的「两件事」成了可以亲手 diff 的实验。最后回扣第 2 章 1.8：生命周期六步里的「验证」一格，展开后就是本章全部内容。

### 1.4 安全模型的边界

背景问题：通过验证等于程序正确吗？不等于。验证器证明「**这一版程序**在**这类输入**下**安全**」——访存有界、必然停机、只调白名单内的能力。三个限定词各有边界：

- 「安全」不含逻辑正确：统计口径写错、规则写反、该丢弃的包放行了——只要访存合法，验证器一律放行（逻辑正确性永远在开发者这边）。
- 「这一版」是字节码级：改一行、重新编译，就要重新验证；证明结论不跟源码走，跟字节码走。
- 「安全」不含数据质量：多 CPU 写竞争导致计数偏少（第 2 章 3.4）、LRU 满表静默淘汰旧表项（第 2 章 3.3）——验证器完全不管这类「安全但不对」。

保守性取舍是安全模型最重要的边界。验证器的回答只有两种：「可证明安全」与「无法证明」，后者一律拒绝——哪怕程序实际安全。最刺眼的代价：**合法程序也可能被拒**。三节画廊就是这份清单的实物化：未判空的查找（3.1）、缺边界检查的报文读（3.2）、对尾界指针的算术（3.3）、分支外读未初始化栈变量（3.4）、上界取自输入的循环（3.5）、白名单外的辅助函数（3.6）、标量当指针解引用（3.7）——七类写法 C 层面都「合法」、clang 都放行，被拒理由全部是「安全不可证明」。保守换来：**拒绝即安全**——内核不必为「没证明到的区域」准备运行时兜底，1.2 的两层防线由此闭合。

**学生动手**：进入三节前，先把自己的直觉当被检对象：写下你预想中「合法但难证明」的三种 C 写法（找不着方向就从这三处想：上界来自输入的循环、值在运行时才确定的数组下标、编译器可能优化掉的检查）。学完三节回来对答案：三种写法各对应画廊哪一对？若有三节没覆盖的，你就找到了画廊之外的类别——带着它去读所用内核的 `Documentation/bpf/verifier.rst` 求证。

检查点（先自答，再看提示）：

1. 验证器的三类安全保证分别挡住什么？各举一个会被该类检查拒绝的写法。（提示：内存安全——不判空就解引用映射值指针；可终止——上界取自报文的循环；权限最小化——调用本程序类型白名单外的辅助函数；现场分别见 3.1/3.2/3.5/3.6。）
2. 数组映射越界下标的查找，为什么不能靠验证器在加载期证明？它由哪层防线兜底、程序侧剩什么义务？（提示：下标值运行时才知道，静态证明无从谈起；辅助函数内部定界返回 NULL——1.2 的运行时定界；程序侧义务是判空。）
3. `bpf()` 返回 `-EPERM` 与 `-EACCES`，分别说明加载路径走到了哪里？排错第一步为什么先分这两者？（提示：`-EPERM` 没进验证——查权限档位；`-EACCES` 进了验证没通过——读日志；两者混着查会浪费时间。）

## 二、验证流水线内核实现分析

一节回答了「验证器做什么」，本节回答「它怎么做」：进入 `kernel/bpf/verifier.c`，沿一次验证的真实顺序拆开流水线——入口与两个核心结构（2.1）、指令级模拟执行的抽象解释原理（2.2）、寄存器状态族（2.3）、控制流探索与剪枝（2.4）、边界推导（2.5）、栈模型与终止性（2.6）、辅助函数约束与日志（2.7）。本节纯讲解，不含加载与挂载操作；凡随内核版本演进的函数名、结构体字段，一律保守措辞并注明「以所用内核源码为准」（讲解以 5.10+ 稳定行为为基准，本机内核 7.0 仅作口径参考）。

### 2.1 验证入口与总体管线

背景问题：一节说的「三类保证」在代码里从哪个函数开始？答案：`kernel/bpf/syscall.c` 的程序加载路径在 license 等属性核对之后，调用 `kernel/bpf/verifier.c` 的 `bpf_check()`——验证的总入口（函数名与调用点以所用内核源码为准；预告⑥的「逐指令模拟执行」从这里开始兑现）。

`bpf_check()` 内部的骨架大致是：先做指令级预处理（重定位一类——map fd 等解析要赶在探索之前，随版本演进），再做控制流图（Control Flow Graph，CFG）检查（跳转落点、回边合法性——2.6 终止性的第一道），然后进入逐指令状态探索主循环（2.2/2.4 的全部内容），通过后做收尾修正（死代码清除、辅助函数内联与上下文访存改写一类）交还加载路径。

理解这条管线，只需要两个核心结构（都声明在 `include/linux/bpf_verifier.h`，字段随版本演进，以所用内核源码为准）：

- **`bpf_verifier_env`**：验证环境——一次验证会话的全部上下文。待验证程序的指针、日志缓冲（`bpf_verifier_log` 一族，2.7）、能力档位标志（特权与否直接改变严格度，2.6/2.7 会两次遇到它）、探索工作栈与当前状态。verifier 的几乎每个函数都以 env 为第一参数——「一次会话」就是这个结构。
- **`bpf_verifier_state`**：探索中的机器状态——某一时刻程序「可能处于」的状态：全部寄存器各自的 `bpf_reg_state`（2.3）加上调用栈帧。探索主循环的基本动作只有一句话：取一条指令，在当前 state 上推演它对 state 的改变。

管线整体形状：

```text
bpf_check()（kernel/bpf/verifier.c）
  ├─ 预处理：重定位一类（map fd 等解析赶在探索前，随版本演进）
  ├─ CFG 检查：跳转落点必须落在程序内；回边按能力档裁决（2.6）
  ├─ 逐指令状态探索主循环（2.2/2.4）
  │    ├─ 每条指令：按寄存器状态族推演效果（2.3）
  │    ├─ 分支：两条路径各自探索；等价状态剪枝（2.4）
  │    └─ 访存裁决：边界推导放行/拒绝（2.5）
  ├─ 收尾修正：死代码清除、辅助函数内联与上下文访存改写一类（随版本演进）
  └─ 结果：通过 → 交还加载路径做 JIT；任一步拒绝 → -EACCES + 日志（1.3）
```

### 2.2 指令级模拟执行

背景问题：不真正执行程序，怎么知道它安全？答案是抽象解释（abstract interpretation）：用「所有可能取值的集合」代替「具体值」来执行程序。真实执行时，寄存器里是一个 64 位数；模拟执行时，「寄存器」里是一段**描述**——类型（标量还是什么指针）、取值范围（上下界）、偏移与对齐。这套描述的载体就是 2.3 的 `bpf_reg_state`。

三类对象的抽象取值域各不相同。寄存器的抽象值 = 类型 + 范围（「标量，范围 [0, 15]」或「报文指针，偏移 [0, 14]」这样的形状）；栈槽是寄存器的溢出位，同一套抽象（2.6 讲栈特有的初始化跟踪）；映射值不像寄存器那样被逐值全程跟踪——它以「定型」为主：是否已判空、大小是否登记（2.3 的映射值类型学）。

为什么「模拟」就能保证「真实执行」安全？这是全书到这里最值得想透的一段论证，关键词是过近似：模拟推演的从来不是某一次输入下的行为，而是**所有可能输入的合取**——抽象值始终是具体值的超集。打个沙盘推演的比方：推演时把敌人可能出现的一切位置都摆上棋子；推演里每一步你都赢（每次访存都合法、每条路径都收敛），实战就不可能输——任何一次真实执行都只是推演的一个特例。反过来，「推演赢不了」不代表「实战会出事」：推演输掉只说明「证明不出来」，这正是 1.4 保守性的来源。

两个推论贯穿二节余下的所有小节：其一，验证器对「具体值」天然失明——凡取决于输入的值都进入范围追踪而不是数值追踪（2.5 的全部内容）；其二，模拟必须覆盖所有路径——多条路径、状态合并与剪枝因此不可避免（2.4）。还有第 2 章 2.1 的那个前提在此兑现（预告④）：这套推演之所以可行，是因为指令集足够小、每条指令语义可枚举——「指令集越小，verifier 能证明的越多」在流水线层面的含义就是：主循环里每种操作码都对应一条有限的推演规则。

### 2.3 寄存器状态族 bpf_reg_state

背景问题：抽象值长什么样？答案集中在 `struct bpf_reg_state`（声明于 `include/linux/bpf_verifier.h`，字段随版本演进）的三块信息里：**类型**（`type` 字段，枚举 `bpf_reg_type`）、**范围**（有符号/无符号上下界一族，外加位级三元抽象 tnum——每一位取「确定 0 / 确定 1 / 未知」，命名随版本演进）、**指针信息**（偏移与定界信息一族）。其中类型是安全模型的主角——一节的三类保证，落到寄存器层面就是一张类型表。5.10+ 稳定核心集如下（枚举成员随内核版本增删，以所用内核源码为准）：

| 类型 | 语义 | 允许的算术 | 要求的检查 |
|---|---|---|---|
| `SCALAR_VALUE` | 纯数值，不指向任何内存 | 任意算术与位运算 | 不可解引用 |
| `PTR_TO_CTX` | 上下文对象指针（按程序类型申报） | 不做自由算术，字段按固定偏移访问 | 访问落在申报的上下文布局内 |
| `CONST_PTR_TO_MAP` | 映射本体指针 | 不可算术、不可解引用 | 主要作为查找类辅助函数的映射参数 |
| `PTR_TO_MAP_KEY` | 映射键指针 | 偏移算术（受限） | 只读，偏移在 key 大小内 |
| `PTR_TO_MAP_VALUE_OR_NULL` | 查找返回：值指针**或** NULL | 不可算术、不可解引用 | 必须判空；判空后收窄为下一行 |
| `PTR_TO_MAP_VALUE` | 已判空的映射值指针 | 偏移算术，越出 value 边界即拒 | 访存偏移落在 value 大小内 |
| `PTR_TO_STACK` | 栈帧指针（r10 派生） | 偏移算术 | 偏移在 512 字节栈内且槽已初始化（2.6） |
| `PTR_TO_PACKET` | 报文数据指针（`data` 派生） | 偏移算术（受界约束） | 先与 `PTR_TO_PACKET_END` 建立关系才可解引用（2.5） |
| `PTR_TO_PACKET_END` | 报文尾界（`data_end`） | **不可算术** | 只参与比较 |
| `PTR_TO_BTF_ID` | 内核结构体指针（按 BTF 类型申报） | 按申报类型的字段偏移 | 访问落在申报类型的布局内 |
| `PTR_TO_MEM` | probe 系辅助函数读入的登记缓冲 | 按登记大小 | 访存落在登记大小内 |
| `NOT_INIT` | 尚未赋值的寄存器 | 不可使用 | 使用即拒（与 2.6 栈未初始化同源） |

读这张表的钥匙在最后两列的分工：「允许的算术」回答类型可否派生新指针，「要求的检查」回答程序要补交哪些证明才能从「弱定型」升级成「强定型」。两个最常用的例子：查找返回的 `PTR_TO_MAP_VALUE_OR_NULL` 必须判空，`if (!v) return ...;` 之后空路径退出、非空路径上类型收窄为 `PTR_TO_MAP_VALUE`——三节 3.1 的 bad 就是没有这一步；`PTR_TO_PACKET_END` 只许比较、不许算术——三节 3.3 的 bad 对它做了加法，日志 `R2 pointer arithmetic on pkt_end PROHIBITED` 一类（预期输出示例 / 运行级待验证；日志行随内核版本略有差异）。

预告⑦之一在此正式作答。第 2 章 5.2 问过：为什么敢直接读 `ctx->next_pid`？任意内核指针为什么必须走 probe 系辅助函数？用这张表回答：ctx 以 `PTR_TO_CTX` 进入程序；程序类型登记时，内核已通过每个类型自己的上下文访问校验回调（`is_valid_access` 一类，随版本演进）向验证器申报了「哪些偏移、什么宽度、读还是写」——对固定偏移的字段读，加载期即可证明落在申报范围内，静态放行、零运行时开销。而把 ctx 里读出的标量（`SCALAR_VALUE`）强转成指针再解引用，在类型学上直接不成立——`SCALAR_VALUE` 不可解引用（三节 3.7 的 `invalid mem access 'scalar'`）。真正的任意内核地址必须经 probe 系辅助函数：由辅助函数在内部定界，把「内核空间任意地址」收窄成 `PTR_TO_MEM` 的登记缓冲。一句话总结：内核不按「地址」管理访问，按「类型 + 申报」管理访问。

### 2.4 控制流探索与状态合并

背景问题：程序有分支，每个分支之后寄存器状态不同——模拟怎么不漏掉任何一条路径？分两步：先建图，再探索。

第一步，CFG 检查：把程序看成有向图（指令是节点，跳转是边），验证「跳转目标必须落在程序内」「回边按能力档裁决」（2.6）。这一步只看图的结构，不看数据。

第二步，从入口开始逐指令探索。遇到条件跳转，验证器把另一条分支连同它的状态压入待探索栈（`push_stack` 一类函数，随版本演进），沿当前路径继续；当前路径走完（退出、或被拒绝）后弹出下一条待探索路径继续。两条路各模拟一遍——不是抽一条代表，是全覆盖。

那「汇合点」呢？概念上，抽象解释在汇合点做保守合并——取两条路径中更宽的口径。Linux 验证器的实现没有显式的合并点：它逐路径探索到底，把「合并」的角色交给**状态等价判断**——新路径推进到某条指令时，若当前状态与这条指令上已经探索过的某状态等价（`regsafe` 一族比较函数，随版本演进），且新状态不比旧状态更宽，则后续执行必然已被覆盖，整段直接跳过。这就是状态剪枝（state pruning），`is_state_visited()` 一类函数是它的家。

状态爆炸（state explosion）为什么没有发生？理论上路径数随分支数指数增长，但剪枝把「等价状态」的后续探索合并掉了；再配两条硬预算：总执行指令预算（百万条量级，随版本调整——日志尾行 `processed N insns (limit ...)` 里的 limit 就是它；预期日志文本，随内核版本略有差异）与每指令状态数、调用栈深度等上限。预算用尽即拒绝加载——「过于复杂」本身也算证明失败，呼应 1.1 的可终止保证。

一句定位精度追踪（precision tracking）：等价判断口径过宽会把不该剪的剪掉（漏掉真错误），验证器在「边界推导依赖某个标量的精确值」时临时收紧等价口径、必要时退回精确探索——机制随版本演进，本节记住「剪枝是保守的、必要时可回退」即可。

本节的探索树与剪枝标记的图形版，见「可视化：验证器状态探索与剪枝」一节的图 1——那里用一个双分支小程序把「两条路各模拟一遍、等价即剪」画成图。

### 2.5 边界推导

背景问题：范围从哪来？沿指令传播——常量装载给出确定值；运算按语义收窄或放宽；值不确定时给最宽范围。三组机制，各配一个本章后面会用到的例子。

**标量范围跟踪**。每个标量同时带着有符号/无符号两套上下界（字段随版本演进）与 2.3 提到的位级抽象。例（三节 3.5 的伏笔）：`n = *(__u32 *)data & 0xF`——按位与沿位级抽象传播：结果的高 28 位确定为 0、低 4 位未知，无符号上界从 2^32−1 一步塌缩到 15（取值域收窄为 [0, 15] 共 16 个可能值）。以 `i < n` 为条件的循环因此可证明至多迭代 15 次——「上界变常数」是掩码指令的直接推论，不是验证器对循环网开一面。掩码位数按业务语义选，上界 = 2^位数 − 1（画廊 3.5 fixed 版注释同口径）。

**报文指针比较建立关系**（三节 3.2 的伏笔）。`data` 与 `data_end` 从上下文读出时，是两个**毫无关系**的指针：一个 `PTR_TO_PACKET`、一个 `PTR_TO_PACKET_END`。一句 `if ((void *)(eth + 1) > data_end) return XDP_PASS;` 之后，「不返回」那条路径上多了一条事实：报文指针的偏移加对象大小，不超过尾界的偏移——**比较建立了两指针的相对关系**，此后的解引用才可证明落在报文内。没有这句比较，关系不存在，第一次越界读即被拒（日志 `R2 offset is outside of the packet` 一类；预期输出示例 / 运行级待验证，随内核版本略有差异）。锚点程序 `book/examples/chapter-03/01-pkt-parse/pkt_parse.bpf.c` 每层协议头一行检查，正是这个机制的三连用——「通过路径」长什么样，本节是它的原理页。

**有符号/无符号与掩码修正**（练习 2 的伏笔）。两套界混用会产生「负偏移」：一个可能为负的值被当作偏移加到指针上，验证器拒绝并给出形如 `R2 min value is negative, either use unsigned or 'var &= const'` 的信号（预期输出示例 / 运行级待验证；日志行随内核版本略有差异）。处理方向两条：改用无符号语义让界对齐，或用掩码把取值域收窄到非负。本章练习 2 就是从这条日志反推根因——把本节机制读成排错能力。

### 2.6 栈模型与终止性

**栈模型**。BPF 栈固定 512 字节（第 2 章 2.1 埋的线头）。验证器对这 512 字节做**栈槽初始化跟踪**：每个槽位只有在「当前这条路径上先写过」之后才允许读；读到从未写过的槽即拒，日志两种形态——针对未初始化寄存器的 `R2 !read_ok` 一类，或按栈槽指认的 `invalid read from stack off ...` 一类（预期输出示例 / 运行级待验证；日志行随内核版本略有差异）。拒绝的理由是安全而不是洁癖：默认配置下内核栈在使用之间不清零，未初始化的槽里可能残留前一次系统调用留下的进程敏感数据，读出并回传用户态就是一次信息泄露。三节 3.4 的 bad（分支外读未初始化栈变量）就是这条规则的现场。

严格度随特权档位变化——这是栈模型里必须点亮的一层：未初始化栈读的拒绝有配置前提。特权加载（`CAP_BPF` 一类能力档）下，验证环境里 `allow_uninit_stack` 一类档位标志置位（字段声明于 `include/linux/bpf_verifier.h`，在 `bpf_check()` 中按能力档赋值——以所用内核源码为准），未初始化栈读被放行：内核认为特权用户本就能读到这类数据，泄露模型对特权档不成立。同一份字节码，允许非特权 BPF 的配置拒绝、特权配置放行——**验证器的严格度随特权档位变化**不是缺陷而是信任模型的一部分；教学与代码审计一律按「必须初始化」对待（画廊 3.4 README 的特权豁免说明同口径）。

**终止性**（预告⑤回收）。第 2 章 2.3 的规则「跳转偏移必须落在程序内、程序必须可证明会终止」在流水线里是两道机制。第一道在 CFG 检查（2.4 第一步）：跳转目标越出程序边界即拒；回边（构成循环的跳转）是否放行，由能力档条件裁决——源码中体现为 `loop_ok` 与 `bpf_capable` 一类条件的组合（以所用内核源码为准）。第二道在状态探索：对放行的回边，验证器不数迭代次数，而是看探索是否收敛——循环体每转一圈，若状态落入已见过的等价状态（或不再变化），探索终止、证明成立；若始终无法收敛，拒绝，日志 `infinite loop detected at insn ...` 一类——这是特权路径的主形态；非特权路径上回边在 CFG 一层就被拒，日志 `back-edge from insn ... to ...` 一类。

版本演进一句话（保守措辞，以所用内核源码与文档为准）：5.3 之前，任何回边一律拒绝——「可证明会终止」靠禁止循环语法实现；5.3 起对特权程序允许有界循环（bounded loop）——语法放开，终止性改由「状态探索是否收敛」裁决。第 2 章那条规则前后两种实现口径，结论不变：无界执行进不来。再加上 2.4 的指令预算兜底，栈限 512 字节、指令预算百万级、循环必须收敛——三者共同把「无界」排除在模型之外。

### 2.7 辅助函数约束、白名单与日志

背景问题：权限最小化（1.1 第三类保证）怎么落地？两个机制：按程序类型登记的白名单，与按参数原型的类型检查。

**白名单按程序类型登记**。每个程序类型在内核里登记一组验证器操作（`bpf_verifier_ops` 一类结构，定义于 `include/linux/filter.h` 一类头文件，字段随版本演进），其中「给定编号，返回该类型的原型或 NULL」一类回调回答了「这个程序类型能否调用编号 N 的辅助函数」——可用面按类型裁剪：XDP 程序调不了 tracing 类的 `bpf_get_current_pid_tgid()`，反之亦然。这是第 2 章 1.3「每个程序类型只能看到自己可用的那部分辅助函数」的机制版（预告②在此回收机制，现场在三节 3.6；预告⑦的辅助函数侧面——probe 系能力的登记——也在此收口）。白名单落空的日志形态：`unknown func bpf_get_current_pid_tgid#14` 一类（预期输出示例 / 运行级待验证；日志行随内核版本略有差异）——注意措辞是「unknown func」而不是「不允许」：白名单按类型正向登记，miss 的含义是「此类型的世界里没有这个函数」。license 在同一层在场：部分原型标记为仅 GPL 兼容 license 可用，不兼容同样拒绝——第 2 章 4.3 第 1 步的回声。

**参数原型与类型检查**。每个可用的辅助函数都有原型（`bpf_func_proto` 一类结构，字段随版本演进）：登记返回值类型与每个参数的类型约束（`ARG_PTR_TO_MAP_KEY`、`ARG_CONST_MAP_PTR`、`ARG_PTR_TO_CTX` 一族）。调用点逐一核对：实参寄存器的当前类型（2.3 表）必须匹配参数约束，常量约束（如缓冲大小须为编译期常量）同样在此核对。这是 2.3 类型学的消费端——那张表「要求的检查」列里，一半义务来自这里的原型。例：`bpf_map_lookup_elem` 的映射参数要求映射本体指针（对应 2.3 的 `CONST_PTR_TO_MAP`）、键参数要求指向键的指针（`ARG_PTR_TO_MAP_KEY`）——把标量传进去即拒；返回值定型为 `PTR_TO_MAP_VALUE_OR_NULL`，判空后才可解引用（1.2/2.3 的闭环）。

**日志如何产生与详细度控制**。验证过程中，逐条日志由 `verbose()` 一类函数写入挂在 `bpf_verifier_env` 上的日志缓冲（2.1 的 env）；每行的典型形态是「指令号 + 执行后的寄存器状态」——2.2/2.3 的推演过程原样落盘，失败时最后一行就是结论。详细度由加载参数的 log_level 档位控制：0 只给结论、1 给逐指令轨迹、2 追加更细的状态信息（档位语义随版本略有差异，以所用内核源码与 UAPI 注释为准）；缓冲区过小则日志被截断。怎么把日志拿到手、`bpftool prog load` 的日志开关、逐行读法——是四节实战的正题，那里把本节机制变成工作流。

**教师视角**：本节的讲解顺序是先类型（2.3）、再流程（2.4）、最后边界与栈（2.5/2.6）——这不是随意编排，而是与验证器的检查顺序同构：**先定性，再定量**。类型不对，一切免谈（`unknown func`、`invalid mem access 'scalar'`）；类型对了，才轮到「这个偏移在不在界内」。读者读日志的排查顺序也应该同构：先认类型错、再查边界错——把 2.3 的表当字典用，把 2.5 的机制当算术用。两个误区：其一，把白名单理解成「黑名单的补集」——它是按程序类型正向登记的能力面，「查无此函数」与「有此函数但不许用」根因不同，修复方向也不同；其二，把日志当报错文本背——日志行随内核版本漂移，值得记的是「信号 → 根因类别」的映射（排错节的速查表干的就是这件事）。

**学生动手**：在本机内核源码或文档中定位 `bpf_reg_state` 的定义，逐项核对 2.3 的表。本机装了内核源码的话，从 `grep -rn "struct bpf_reg_state" /usr/src/` 入手；没有源码就在文档站点按你的内核版本检索 `include/linux/bpf_verifier.h`。核对时盯三处：枚举成员的增删（2.3 表尾注）、范围字段一族（有符号/无符号上下界）的命名、指针偏移与位级抽象的拆分方式。把与 2.3 表不一致的条目记下来——「表会随版本漂移，并且你核对过当前版本」这件事本身，就是本章要教给你的能力。无源码环境的替代路径：读所用内核的 `Documentation/bpf/verifier.rst`，与 2.2/2.4 的机制对照。

检查点（先自答，再看提示）：

1. 同一个 XDP 程序调用 `bpf_get_current_pid_tgid()`，编译期与加载期各发生什么？日志大致长什么样？（提示：编译期不报错——原型都在头文件里，clang 不做白名单检查（第 2 章 1.3）；加载期白名单落空，日志 `unknown func ...#<id>` 一类（预期日志文本，随内核版本略有差异）——白名单按程序类型正向登记。）
2. `PTR_TO_MAP_VALUE_OR_NULL` 与 `PTR_TO_MAP_VALUE` 的差别是什么？哪一个可以直接解引用？（提示：前者是查找返回的「值或 NULL」联合定型，必须判空收窄成后者；直接解引用前者，就是三节 3.1 的 `invalid mem access 'map_value_or_null'`（预期日志文本，随内核版本略有差异）。）
3. 为什么「模拟执行」敢替「真实执行」作保？一句话说出过近似的方向。（提示：抽象值始终是具体值的超集——推演覆盖所有可能输入；推演中每步合法，真实执行作为特例不可能不合法。）
4. 512 字节栈限、百万条指令预算、循环必须收敛——三者共同把什么排除在模型之外？（提示：「无界」；这是 1.1 可终止保证的三道预算化机制——2.4/2.6。）

## 三、失败画廊：七类典型拒绝

一节把「合法但难证明」的写法列成了七类清单（1.4），本节把这七类做成七个现场：每类先看一份 clang 编译通过的 bad 程序——语法无懈可击，只在加载期被验证器拦下——再对照它的最小修复版 fixed，两份源码 diff 只差一处语义。全部素材落在 [`book/examples/chapter-03/02-fail-gallery/`](../examples/chapter-03/02-fail-gallery/)：七对目录各自含 bad.bpf.c、fixed.bpf.c、Makefile 与 README，只编译不加载（compile-only），bad 程序的验收口径就是「编译成功」。走读顺序按「从最常见到最隐蔽」排列：判空（3.1）→ 报文边界（3.2）→ 指针算术（3.3）→ 栈初始化（3.4）→ 终止性（3.5）→ 白名单（3.6）→ 任意地址（3.7）。每个 card 固定六段：背景问题 → bad 代码全文 → 预期 verifier 日志关键行 → 为什么拒绝（回指二节原理小节）→ fixed 修复片段 → 修复原则一句话。日志口径全节统一：凡日志均为预期输出示例 / 运行级待验证，日志行随内核版本略有差异（以 5.10+ 稳定措辞为基准）——读日志认「信号 → 根因类别」的映射，不背文本（2.7 教师视角同口径）。

### 3.1 未检查的映射查找（画廊 01）

背景问题：`bpf_map_lookup_elem` 是 BPF 程序与数据面交互的第一入口，也是初学者写下的第一行「会出事的代码」。第 2 章 3.2 给过标准样本：数组映射对越界下标的查找不报错，而是在辅助函数内部定界、返回 NULL；1.2 由此把「判空」定为程序侧硬性义务。本对展示不履行义务的现场——对查找返回值直接 `*v += 1`。

bad 程序全文（画廊 01 目录：[`book/examples/chapter-03/02-fail-gallery/01-map-null/`](../examples/chapter-03/02-fail-gallery/01-map-null/)；下贴 `book/examples/chapter-03/02-fail-gallery/01-map-null/bad.bpf.c`）：

```c
// SPDX-License-Identifier: GPL-2.0 OR BSD-3-Clause
/*
 * 画廊 01-map-null / bad：预期被拒：map_value_or_null 直接解引用。
 *
 * verifier 为什么会拒绝：bpf_map_lookup_elem 这个辅助函数（helper）的返回值天然
 *   可能是 NULL——key 不在映射（map）里、key 越界（本例 array 映射只有 1 个槽）
 *   都查不到。因此返回值寄存器的类型是 map_value_or_null：「映射值指针 或 NULL」
 *   两态合一。验证器（verifier）按最坏情况证明安全：不判空就 *v += 1，存在对
 *   NULL 解引用的路径——内核态空指针访问会让内核崩溃，违反「已验证程序不可能
 *   崩溃内核」的安全承诺，所以必须在加载期拒绝，而不是等运行时出错。
 *
 * 本文件在 clang 层面完全合法（编译通过）；拒绝发生在加载期。修复形态见同目录
 * fixed.bpf.c——仅插入一个 NULL 分支；卡片讲解见本目录 README.md。
 */
#include "vmlinux.h"
#include <bpf/bpf_helpers.h>

/* uapi 常量不在 vmlinux.h 中（BTF 只含类型），画廊 XDP 类骨架统一手工定义 */
#define ETH_P_IP 0x0800
#define IPPROTO_UDP 17

/* 画廊公共 stats map 块：单槽 array 映射计数器——本对的错误点不在 map 本身，
 * 而在 lookup 返回值的处理，故保留最简形态 */
struct {
    __uint(type, BPF_MAP_TYPE_ARRAY);
    __uint(max_entries, 1);
    __type(key, __u32);
    __type(value, __u64);
} stats SEC(".maps");

SEC("xdp")
int probe_bad(struct xdp_md *ctx)
{
    __u32 key = 0;
    __u64 *v = bpf_map_lookup_elem(&stats, &key);
    *v += 1;                       /* 预期被拒：返回值可能是 NULL，直接解引用 */
    return XDP_PASS;
}

char LICENSE[] SEC("license") = "GPL";
```

预期 verifier 日志关键行（预期输出示例 / 运行级待验证；日志行随内核版本略有差异）：

```text
invalid mem access 'map_value_or_null'
```

关键行指认「对处于 map_value_or_null 状态的寄存器做了不允许的内存访问」，日志前文会列出对应的指令与寄存器状态（格式随版本略有差异）。

为什么拒绝：回到 2.3 的类型表——查找返回值定型为 `PTR_TO_MAP_VALUE_OR_NULL`，语义是「映射值指针 或 NULL」两态合一，「要求的检查」一列写明必须判空：`if (!v)` 的空路径退出后，非空路径上类型收窄为 `PTR_TO_MAP_VALUE`，解引用才可证明安全。bad 跳过收窄直接解引用，而验证器按最坏情况证明：key 查不到的路径上这就是一次内核态空指针访问，违反第一类安全保证（1.1）——必须在加载期拒绝，而不是等运行时出错。这正是 1.2 两层防线分工的程序侧落点：内核把「下标是否越界」下沉到辅助函数内部裁决（第 2 章 3.2 的运行时定界），调用方的义务就是判空——类型系统的定型要求，不是风格偏好（锚点 `01-pkt-parse` 里 `if (count)` 的防御式判空是同一模式的冗余变体，1.2 的调停口径）。

fixed 修复片段（下贴 `book/examples/chapter-03/02-fail-gallery/01-map-null/fixed.bpf.c` 的 `probe_fixed` 函数；映射定义与 license 与 bad 一致）：

```c
SEC("xdp")
int probe_fixed(struct xdp_md *ctx)
{
    __u32 key = 0;
    __u64 *v = bpf_map_lookup_elem(&stats, &key);
    if (!v)
        return XDP_PASS;           /* 修复：NULL 分支让类型从 map_value_or_null 定型为 map_value */
    *v += 1;
    return XDP_PASS;
}
```

修复原则一句话：**lookup 之后、解引用之前先判空 `if (!v) return ...;`**——判空让类型从 map_value_or_null 定型为 map_value；NULL 分支的返回动作按业务语义选择，同型错误（`bpf_ringbuf_reserve` 等可能返回 NULL 的返回值）遵循同一原则。

### 3.2 报文边界检查缺失（画廊 02）

背景问题：报文解析是 XDP 程序的本职，也是被拒率最高的一类写法——报文长度运行时才确定，随时可能被硬件或上游截断，最小以太网帧都可能不完整。正面锚点 `01-pkt-parse` 已示范「通过路径」长什么样；本对把同类解析的界检查全部删掉，看验证器看到的世界。

bad 程序全文（画廊 02 目录：[`book/examples/chapter-03/02-fail-gallery/02-pkt-bounds/`](../examples/chapter-03/02-fail-gallery/02-pkt-bounds/)；下贴 `book/examples/chapter-03/02-fail-gallery/02-pkt-bounds/bad.bpf.c`）：

```c
// SPDX-License-Identifier: GPL-2.0 OR BSD-3-Clause
/*
 * 画廊 02-pkt-bounds / bad：预期被拒：报文边界检查缺失——首个越界读在 eth->h_proto。
 *
 * verifier 为什么会拒绝：packet 指针（从 ctx->data 起）指向长度可变的报文，网络
 *   报文随时可能被硬件/上游截断，验证器（verifier）无法凭「一般报文够长」放行——
 *   每个字段的读偏移都必须先与 data_end 界标比较、证明落在报文内。本程序把
 *   eth/ip 两层指针推进后未做任何 (void *)(指针 + 1) > data_end 检查就读字段，
 *   第一个字段读 eth->h_proto（偏移 12..13）时已不可证明在报文内——越界读会泄出
 *   报文缓冲区之外的内核内存，因此加载期直接拒绝。
 *
 * 对照通过路径锚点 ../../01-pkt-parse/pkt_parse.bpf.c：同一解析链，每层解引用前
 * 先做界检查即放行。本文件在 clang 层面完全合法（编译通过）；修复形态见同目录
 * fixed.bpf.c——仅插入两层界检查；卡片讲解见本目录 README.md。
 */
#include "vmlinux.h"
#include <bpf/bpf_helpers.h>
#include <bpf/bpf_endian.h>    /* bpf_htons：h_proto 为网络字节序 */

/* uapi 常量不在 vmlinux.h 中（BTF 只含类型），画廊 XDP 类骨架统一手工定义 */
#define ETH_P_IP 0x0800
#define IPPROTO_UDP 17

SEC("xdp")
int probe_bad(struct xdp_md *ctx)
{
    void *data = (void *)(long)ctx->data;
    void *data_end = (void *)(long)ctx->data_end;
    struct ethhdr *eth = data;
    struct iphdr *ip = data + sizeof(*eth);
    if (eth->h_proto == bpf_htons(ETH_P_IP) && ip->protocol == IPPROTO_UDP)
        return XDP_DROP;           /* 预期被拒：首个越界读在 eth->h_proto（无任何 data_end 检查） */
    return XDP_PASS;
}

char LICENSE[] SEC("license") = "GPL";
```

程序把 `eth`、`ip` 两层指针推进后直接读字段，全程没有一次与 `data_end` 的比较——首个越界读在 `eth->h_proto`（bad 头注释同口径）。

预期 verifier 日志关键行（预期输出示例 / 运行级待验证；日志行随内核版本略有差异）：

```text
R2 offset is outside of the packet
```

关键行指认「寄存器 R2 的偏移已超出报文范围」（部分版本作等价措辞 `invalid packet access`），指认点就是第一个无检查的字段读。一个读日志的提醒：寄存器编号随编译器的寄存器分配变化——同一份源码换 clang 版本、或加删一行无关语句，`R2` 就可能变成 `R1`/`R3`；认措辞与偏移语义，别认编号。

为什么拒绝：2.5 讲过原理——`data` 与 `data_end` 从上下文读出时是两个毫无关系的指针，只有一句 `if ((void *)(eth + 1) > data_end)` 这样的比较，才能在「不返回」的路径上建立「报文指针偏移加对象大小，不超过尾界偏移」的事实，此后的解引用才可证明落在报文内。bad 一次比较都没有，第一个字段读 `eth->h_proto`（偏移 12..13）就处于不可证明状态：报文若短于 14 字节，这次读会越过报文缓冲区、泄出缓冲区之外的内核内存（信息泄露，2.6 同一模型）。验证器按最坏情况证明，不赌「报文一般够长」。对照锚点 `book/examples/chapter-03/01-pkt-parse/pkt_parse.bpf.c`：同一个检查在「通过路径」的位置就是每层解引用前的那一行——本对 fixed 插入的两层检查与锚点的一、二层逐字同形，差别只在命中 UDP 时返回 `XDP_DROP`。

fixed 修复片段（下贴 `book/examples/chapter-03/02-fail-gallery/02-pkt-bounds/fixed.bpf.c` 的 `probe_fixed` 函数；license 与 bad 一致）：

```c
SEC("xdp")
int probe_fixed(struct xdp_md *ctx)
{
    void *data = (void *)(long)ctx->data;
    void *data_end = (void *)(long)ctx->data_end;
    struct ethhdr *eth = data;
    if ((void *)(eth + 1) > data_end)      /* 修复①：第一层界检查——以太网头（14 字节）完整落在报文内才可读 */
        return XDP_PASS;
    struct iphdr *ip = data + sizeof(*eth);
    if ((void *)(ip + 1) > data_end)       /* 修复②：第二层界检查——IPv4 头完整落在报文内才可读 */
        return XDP_PASS;
    if (eth->h_proto == bpf_htons(ETH_P_IP) && ip->protocol == IPPROTO_UDP)
        return XDP_DROP;                   /* 与 bad 相同的判定与动作，此时读取已被界检查证明安全 */
    return XDP_PASS;
}
```

修复原则一句话：**每层协议头解引用前，先做整层界检查 `(void *)(指针 + 1) > data_end`**——用「下一层头尾」证明整层落在报文内；上一层检查通过不代表下一层安全，推进模式是「上一层尾 = 这一层头」。

### 3.3 对报文尾界的无效指针运算（画廊 03）

背景问题：看完 3.2 读者可能想「优化」：与其每层比较，不如先把 `data_end` 挪 4 字节再统一比？这一步恰好踩在类型系统最敏感的位置——对尾界指针本身做算术。它不是「忘了检查」，而是结构性不可证明，「补一个检查」豁免不了。

bad 程序全文（画廊 03 目录：[`book/examples/chapter-03/02-fail-gallery/03-ptr-math/`](../examples/chapter-03/02-fail-gallery/03-ptr-math/)；下贴 `book/examples/chapter-03/02-fail-gallery/03-ptr-math/bad.bpf.c`）：

```c
// SPDX-License-Identifier: GPL-2.0 OR BSD-3-Clause
/*
 * 画廊 03-ptr-math / bad：预期被拒：pkt_end 指针禁止算术。
 *
 * verifier 为什么会拒绝：ctx->data_end 是报文尾界（pkt_end）——验证器（verifier）
 *   信任模型的锚点：整个「报文内安全」的证明全部建立在「指针与 data_end 比较」
 *   之上。若允许对尾界本身做算术（data_end += 4），程序就能挪动界标、把越界访问
 *   伪造成「界内」，尾界的可信性即告失效。因此内核把尾界寄存器的类型
 *   （PTR_TO_PACKET_END）登记为不可参与算术——加载期直接拒绝，而不是放行一个
 *   可能被篡改的界标。需要越过若干字节时，把算术放在 packet 指针上并立刻用界
 *   检查收口（见同目录 fixed.bpf.c）。
 *
 * 可观测性说明：紧随其后的比较消费了算术结果——这不是修复，而是防止 clang -O2 把
 *   未使用的 data_end += 4 当死代码消除（消除后产物里没有这条 offending 指令，
 *   加载期也就看不到拒绝）。比较行写作 data > data_end 而非 data + 4 > data_end：
 *   两侧偏移不等（0 对 4），编译器无法折叠公共偏移，算术指令得以保留；真正被拒
 *   的仍是对尾界的算术本身。本文件在 clang 层面完全合法（编译通过）；拒绝发生在
 *   加载期。卡片讲解见本目录 README.md。
 */
#include "vmlinux.h"
#include <bpf/bpf_helpers.h>

/* uapi 常量不在 vmlinux.h 中（BTF 只含类型），画廊 XDP 类骨架统一手工定义 */
#define ETH_P_IP 0x0800
#define IPPROTO_UDP 17

SEC("xdp")
int probe_bad(struct xdp_md *ctx)
{
    void *data = (void *)(long)ctx->data;
    void *data_end = (void *)(long)ctx->data_end;
    data_end += 4;                 /* 预期被拒：pkt_end 指针禁止算术（内核以此保住报文尾界的可信性） */
    if (data > data_end)           /* 算术结果参与比较：防止 clang -O2 死代码消除掉 offending 指令 */
        return XDP_DROP;
    return XDP_PASS;
}

char LICENSE[] SEC("license") = "GPL";
```

先读头注释与两个行内注释的分工：`data_end += 4` 是被拒的肇事指令（offending 指令）；紧随其后的 `if (data > data_end)` **不是修复、也不是业务逻辑**，而是可观测性装置——若算术结果无人消费，clang -O2 会把 `data_end += 4` 当死代码消除，产物里没有这条指令、加载期也就看不到拒绝；比较行故意写成偏移不等的 `data > data_end`（0 对 4），编译器无法折叠公共偏移，肇事指令才得以保留。真正被拒的仍是对尾界算术这一条——**不要把「加一个消费比较」误学成修复模式**。

预期 verifier 日志关键行（预期输出示例 / 运行级待验证；日志行随内核版本略有差异）：

```text
R2 pointer arithmetic on pkt_end PROHIBITED
```

这是少数直接在寄存器类型层面（而非访存层面）给出的拒绝，日志会带上肇事指令 `data_end += 4` 的位置；寄存器编号同样随分配变化（实测产物中 `data_end` 分配在 r1）——认措辞，不认编号。

为什么拒绝：2.3 类型表里 `PTR_TO_PACKET_END` 一行的「允许的算术」一栏写着**不可算术**，理由是信任模型而非保守癖：验证器对报文内存安全的全部证明——「读偏移落在 `[data, data_end)` 内」——都建立在尾界**可信**的前提上（2.5 的关系推导以尾界为比较基准）；一旦允许 `data_end += 4`，程序就能挪动界标、把越界访问伪造成「界内」，整个证明的地基即被抽掉。对照 2.3 表的另一行：packet 指针（`PTR_TO_PACKET`，`ctx->data` 一侧）**允许**算术，只是结果的后续访问必须仍受界检查约束——bad 与 fixed 的分界不在「想做偏移运算」，在「对界标本身做运算」。

fixed 修复片段（下贴 `book/examples/chapter-03/02-fail-gallery/03-ptr-math/fixed.bpf.c` 的 `probe_fixed` 函数）：

```c
SEC("xdp")
int probe_fixed(struct xdp_md *ctx)
{
    void *data = (void *)(long)ctx->data;
    void *data_end = (void *)(long)ctx->data_end;
    if (data + 4 > data_end)       /* 修复：算术放在 packet 指针上，且立刻用界检查收口 */

    return XDP_PASS;
}
```

修复原则一句话：**算术放在 packet 指针上，`data_end` 全程只读、只作比较**——需要越过 N 字节时写 `if (data + N > data_end)`，一条语句同时完成「做算术」与「证安全」；算术之后立即收口，否则落回 3.2 的拒绝。

### 3.4 栈变量未初始化使用（画廊 04）

背景问题：变量只在某个分支里赋值、分支外使用——C 初学者的经典错误。在用户态程序里它读到的是垃圾值；在 BPF 程序里，栈上从未写过的槽残留着**前一次系统调用留下的进程敏感数据**（地址、凭据片段），读出并回传用户态就是一次内核信息泄露——这不是正确性问题，是安全问题。

bad 程序全文（画廊 04 目录：[`book/examples/chapter-03/02-fail-gallery/04-stack-uninit/`](../examples/chapter-03/02-fail-gallery/04-stack-uninit/)；下贴 `book/examples/chapter-03/02-fail-gallery/04-stack-uninit/bad.bpf.c`）：

```c
// SPDX-License-Identifier: GPL-2.0 OR BSD-3-Clause
/*
 * 画廊 04-stack-uninit / bad：预期被拒：栈变量仅在 if (v) 分支赋值，分支外使用可能未初始化。
 *
 * verifier 为什么会拒绝：验证器（verifier）对 512 字节栈的每个槽位都跟踪初始化状态
 *   （栈槽的初始化跟踪，见正文 2.6）。本程序里 verdict 只在 if (v) 分支内被写入；
 *   v == NULL（key 不在映射（map）里、映射内存紧张等都查不到）的那条路径上没有

 */
#include "vmlinux.h"
#include <bpf/bpf_helpers.h>

#define ETH_P_IP 0x0800
#define IPPROTO_UDP 17

/* 画廊公共 stats map 块：单槽 array 映射——本对的错误点不在 map 本身，
 * 而在 lookup 返回值的条件赋值与栈初始化跟踪 */
struct {
    __uint(type, BPF_MAP_TYPE_ARRAY);
    __uint(max_entries, 1);
    __type(key, __u32);
    __type(value, __u64);
} stats SEC(".maps");

SEC("xdp")
int probe_bad(struct xdp_md *ctx)
{
    __u32 key = 0;
    volatile __u64 verdict;        /* 预期被拒：仅在 if (v) 分支赋值，分支外使用可能未初始化（volatile 抑制编译器 UB 折叠，见头注释） */
```

先读头注释的可观测性说明：声明行的 `volatile` **不是修复、也不是语义错误的一部分**——未初始化读在 C 里是未定义行为，clang -O2 会把「分支外使用未初始化值」按未定义值折叠（实测：折叠后产物里没有那条未初始化读，整个程序反而变成验证器可放行的形态）；`volatile` 让每次读写落到真实栈槽，未初始化栈槽读取这条肇事指令才得以保留。fixed 侧同样带 `volatile`，使 diff 只剩 `= 0` 一处。

```text

```

```text

```

前者针对未初始化（`NOT_INIT`，与 2.3 表末行同源）的寄存器给出寄存器号，后者无寄存器号、按栈槽偏移与读取尺寸指认——寄存器号与偏移随产物代码生成与内核版本而异（本对 bad 产物实测：栈槽偏移 -16、尺寸 8）。

**特权豁免（重要教学内容）**：上述拒绝有配置前提——仅在允许非特权 BPF 的配置（`kernel.unprivileged_bpf_disabled=0`，即非特权用户可加载 BPF）下成立。特权加载（CAP_PERFMON 一类能力档）下，验证环境的 `allow_uninit_stack` 一类档位标志置位，未初始化栈读被放行——内核认为特权用户本就能读取此类数据，泄露模型对特权档不成立（2.6 的机制讲解）。同一份字节码，非特权路径拒绝、特权路径放行——2.6 点亮的「验证器严格度随特权档位变化」在这对上现场化；教学与代码审计一律按「必须初始化」对待，不依赖特权豁免。

### 3.5 不可证明终止的循环（画廊 05）

背景问题：循环上界取自报文内容——「报文一般不长」是直觉，但攻击者完全可以构造一个 4 字节头、`n = 0xFFFFFFFF` 的报文；一个被放行的 n 次循环会把 CPU 永久卡死在收包软中断里——拒绝服务（Denial of Service，DoS）。可终止是 1.1 的第二类安全保证，验证器必须证明「必然停机」才放行。

bad 程序全文（画廊 05 目录：[`book/examples/chapter-03/02-fail-gallery/05-loop/`](../examples/chapter-03/02-fail-gallery/05-loop/)；下贴 `book/examples/chapter-03/02-fail-gallery/05-loop/bad.bpf.c`）：

```c
// SPDX-License-Identifier: GPL-2.0 OR BSD-3-Clause
/*
 * 画廊 05-loop / bad：预期被拒：循环上界取自报文且无掩码，迭代次数不可证明。
 *
 * verifier 为什么会拒绝：循环体是一条回跳的 back-edge——验证器（verifier）要么证明
 *   循环必然终止（有界循环，5.3 起支持），要么拒绝。本程序循环上界 n 直接取自
 *   报文内容（*(u32 *)data，最大可达 2^32-1），且没有任何掩码收窄：验证器对 n 的
 *   取值推导只能得到「任意 32 位无符号数」，无法证明迭代有界。看似「报文一般
 *   不长」没有用——最坏情况证明要求覆盖攻击者构造的超长迭代：一个被放行的
 *   n 次循环会把 CPU 卡在收包软中断里，即拒绝服务（DoS），所以加载期直接拒绝。
 *
 * 可观测性说明：循环累加写作 sum ^= i 而非 sum += i——这不是修复的一部分，而是
 *   编译级装置：+= 是线性递推，clang -O2 的归纳变量优化（-indvars）会算出闭式
 *   n*(n-1)/2、把循环整条消除（实测：产物里没有任何 back-edge，程序反而变成
 *   验证器可放行的形态）；XOR 递推没有闭式，循环得以保留。if (sum == 0xdeadbeef)
 *   消费循环结果，同样防止循环体被当死代码删除。本文件在 clang 层面完全合法
 *   （编译通过）；拒绝发生在加载期。修复形态见同目录 fixed.bpf.c——仅加一处
 *   掩码；卡片讲解见本目录 README.md。
 */
#include "vmlinux.h"
#include <bpf/bpf_helpers.h>

/* uapi 常量不在 vmlinux.h 中（BTF 只含类型），画廊 XDP 类骨架统一手工定义 */
#define ETH_P_IP 0x0800
#define IPPROTO_UDP 17

SEC("xdp")
int probe_bad(struct xdp_md *ctx)
{
    void *data = (void *)(long)ctx->data;
    void *data_end = (void *)(long)ctx->data_end;
    if (data + 4 > data_end)
        return XDP_PASS;
    __u32 n = *(__u32 *)data;      /* 预期被拒：上界取自报文且无掩码，迭代次数不可证明 */
    __u64 sum = 0;
    for (__u32 i = 0; i < n; i++)
        sum ^= i;                  /* XOR 而非 +=：线性递推会被 -indvars 折叠成闭式、循环整条消除（见头注释可观测性说明） */
    if (sum == 0xdeadbeef)         /* 消费 sum，防止被优化删除 */
        return XDP_DROP;
    return XDP_PASS;
}

char LICENSE[] SEC("license") = "GPL";
```

先读头注释的可观测性说明：循环累加写作 `sum ^= i` **不是修复的一部分**——`+=` 是线性递推，clang -O2 的归纳变量优化（-indvars）会算出闭式、把循环整条消除（实测：产物里没有任何回边，程序反而变成可放行形态）；XOR 递推没有闭式，循环才得以保留，`if (sum == 0xdeadbeef)` 消费循环结果同理防止死代码删除。

预期 verifier 日志关键行（预期输出示例 / 运行级待验证；日志行随内核版本略有差异）：

```text
infinite loop detected at insn 12
```

主形态与路径档位有关（2.6）：特权路径上回边被放行进入状态探索，取值域无法收敛到「有限次迭代必退出」时，以 `infinite loop detected at insn ...` 拒绝——insn 编号锚定循环回边所在，随产物与内核版本而异（本对 bad 产物实测：第 12 条指令回跳第 10 条）；非特权路径对回边在 CFG 一层直接严查，形态为 `back-edge from insn ... to ...`。两类路径的拒绝根因相同：循环不可证明终止。

为什么拒绝：2.6 终止性的第二道机制——验证器对放行的回边不数迭代次数，看**状态探索是否收敛**；收敛的前提是上界可推导，而本例 `n` 从报文读入且无任何收窄，2.5 的边界推导只能给出「[0, 2^32−1] 中的任意值」，最坏 40 亿次迭代不可证明有界。版本演进一句话（保守措辞，以所用内核文档为准）：5.3 之前任何回边一律拒绝，终止性靠禁止循环语法实现；5.3 起对特权程序允许有界循环，终止性改由探索收敛裁决；5.17 起还可用辅助函数 `bpf_loop` 把复杂迭代交给内核。结论不变：无界执行进不来（2.6 的三道预算化机制在此收口）。

fixed 修复片段（下贴 `book/examples/chapter-03/02-fail-gallery/05-loop/fixed.bpf.c` 的 `probe_fixed` 函数；界检查、循环结构与消费语句与 bad 完全一致）：

```c
SEC("xdp")
int probe_fixed(struct xdp_md *ctx)
{
    void *data = (void *)(long)ctx->data;
    void *data_end = (void *)(long)ctx->data_end;
    if (data + 4 > data_end)
        return XDP_PASS;
    __u32 n = *(__u32 *)data & 0xF;   /* 修复：掩码定界，上界收窄到 [0, 15]（迭代至多 15 次），循环可证明终止 */
    __u64 sum = 0;
    for (__u32 i = 0; i < n; i++)
        sum ^= i;                  /* 与 bad 相同：XOR 防止归纳变量优化把循环折叠成闭式 */
    if (sum == 0xdeadbeef)
        return XDP_DROP;
    return XDP_PASS;
}
```

修复原则一句话：**上界先收窄再进循环**——`n & 0xF` 让按位与沿位级抽象传播（2.5 的伏笔例），上界塌缩到 [0, 15]、迭代至多 15 次，可证明终止；掩码位数按业务语义选，上界 = 2^位数 − 1。

### 3.6 辅助函数白名单越界（画廊 06）

背景问题：想在 XDP 程序里按进程聚合统计？`bpf_get_current_pid_tgid()` 在 tracing 程序里天天在用，搬进 XDP 就加载失败——而 clang 一声不吭。第 2 章 1.3 末的预告②「调用当前程序类型不支持的辅助函数，编译期不报错、加载时被拒」在此兑现，这也是 1.3「两件事」最干净的现场：clang 只负责把 call 翻译成「调用辅助函数 id 14」，白名单核对发生在加载期。

bad 程序全文（画廊 06 目录：[`book/examples/chapter-03/02-fail-gallery/06-helper-misuse/`](../examples/chapter-03/02-fail-gallery/06-helper-misuse/)；下贴 `book/examples/chapter-03/02-fail-gallery/06-helper-misuse/bad.bpf.c`）：

```c
/*
 * 画廊 06-helper-misuse / bad：预期被拒：tracing 类专用 helper 不在 XDP 程序类型的白名单。
 *
 * verifier 为什么会拒绝：辅助函数（helper）不是全局可用——内核按程序类型（program
 *   type）登记各自的 helper 白名单（verifier_ops，见正文 2.7）。bpf_get_current_pid_tgid()
 *   读取「当前进程上下文」，只有 tracing/kprobe 等挂在进程上下文里的程序类型才有
 *   语义；XDP 程序跑在网卡收包软中断里，没有「当前进程」可言——放行它不仅语义
 *   错乱，还会把任意进程的 pid/tgid 泄露给网卡路径上的程序。验证器在加载期检查
 *   每条 call 指令：helper id 不在本程序类型的白名单内即拒绝。
 *
 * 本文件在 clang 层面完全合法（编译通过）——clang 只负责把 call 翻译成
 *   「调用 helper id 14」，白名单核对发生在加载期。修复形态见同目录 fixed.bpf.c
 *   ——改用 XDP 白名单内的等价能力；卡片讲解见本目录 README.md。
 */
#include "vmlinux.h"
#include <bpf/bpf_helpers.h>

/* uapi 常量不在 vmlinux.h 中（BTF 只含类型），画廊 XDP 类骨架统一手工定义 */
#define ETH_P_IP 0x0800
#define IPPROTO_UDP 17

SEC("xdp")
int probe_bad(struct xdp_md *ctx)
{
    __u32 pid = (__u32)bpf_get_current_pid_tgid();  /* 预期被拒：tracing 类专用 helper，不在 XDP 白名单 */
    if (pid)
        return XDP_DROP;
    return XDP_PASS;
}

char LICENSE[] SEC("license") = "GPL";
```

预期 verifier 日志关键行（预期输出示例 / 运行级待验证；日志行随内核版本略有差异）：

```text
unknown func bpf_get_current_pid_tgid#14
```

5.10+ 内核源码中，白名单 miss 的唯一输出形态就是 `unknown func <名字>#<id>`——早期教学材料流传的「cannot use helper / not allowed for program type」措辞已不存在于内核源码。**排歧点（初学者最容易误判的地方）**：不要把 `unknown func` 读成「辅助函数不存在」——`bpf_get_current_pid_tgid` 当然存在，「unknown」修饰的是「对本程序类型不可用」，不是「内核没有这个函数」；排查这类拒绝先查辅助函数的程序类型适用面（`include/uapi/linux/bpf.h` 注释或 `bpftool feature probe`），不要先怀疑内核版本。

为什么拒绝：2.7 的机制——白名单按程序类型正向登记，每个程序类型登记一组验证器操作，「给定编号，返回该类型的原型或 NULL」一类回调回答「这个类型能否调用编号 N」。白名单不是官僚关卡，它跟着**执行上下文**走：`bpf_get_current_pid_tgid()` 读的是「当前进程」的 pid/tgid，tracing/kprobe 类程序挂在进程上下文的事件上，「当前进程」有意义；XDP 程序跑在网卡收包软中断里，可能在任意进程的地址空间切换间隙执行——「当前进程」要么无意义、要么指向毫不相关的进程，放行还等于把系统内任意进程的 pid 泄露给网卡路径上的程序。验证器在加载期扫到 call 指令、查出 id、比对清单，不在即拒——不需要等运行时才发现「数据没意义」。

fixed 修复片段（下贴 `book/examples/chapter-03/02-fail-gallery/06-helper-misuse/fixed.bpf.c` 的 `probe_fixed` 函数；判定结构与返回动作与 bad 一致）：

```c
SEC("xdp")
int probe_fixed(struct xdp_md *ctx)
{
    __u32 cpu = bpf_get_smp_processor_id();         /* 修复：改用 XDP 白名单内的等价能力 */
    if (cpu)
        return XDP_DROP;
    return XDP_PASS;
}
```

修复原则一句话：**先查适用面再选辅助函数**——拿不准就换同程序类型白名单内的等价能力（按 pid 聚合换不成，就按 CPU 聚合）；这是语义替换、不是绕过——白名单没有豁免机制，直接改 helper id 硬绕，会在参数原型检查处再次被拒（2.7）。

### 3.7 ctx 标量强转指针直接解引用（画廊 07）

背景问题：最后一类最隐蔽——tracepoint 上下文的 `args[]` 字段**在数值上**存着合法的用户态地址（本例是 openat 的 filename 参数），C 强转成指针就能用，编译器放行。但「数值上像指针」与「类型上是指针」是两回事——这正是第 2 章 5.2 预告⑦之一「ctx 申报访问与任意内核指针 probe 界限的分界，证明过程是第 3 章正题」的正式兑现。

bad 程序全文（画廊 07 目录：[`book/examples/chapter-03/02-fail-gallery/07-kernel-ptr/`](../examples/chapter-03/02-fail-gallery/07-kernel-ptr/)；下贴 `book/examples/chapter-03/02-fail-gallery/07-kernel-ptr/bad.bpf.c`）：

```c
// SPDX-License-Identifier: GPL-2.0 OR BSD-3-Clause
/*
 * 画廊 07-kernel-ptr / bad：预期被拒：ctx 标量字段强转指针后直接解引用。
 *
 * verifier 为什么会拒绝：tracepoint 上下文（struct trace_event_raw_sys_enter）的
 *   args[] 字段是「指针的数值」——寄存器类型是标量（SCALAR_VALUE），不是任何
 *   可解引用的指针类型。验证器（verifier）的类型系统只允许解引用「登记过的指针」：
 *   ctx 本身可按布局访问（申报访问），而 ctx 字段里存着的内核/用户地址属于
 *   「任意地址」，直接解引用 = 允许 BPF 程序读内核里任何位置（任意读漏洞），
 *   因此加载期拒绝。任意地址必须走 probe 系辅助函数（helper）（bpf_probe_read_user_str
 *   等，helper 内部做受界限检查——第 2 章预告⑦的兑现，正文 2.3 寄存器类型表）。
 *
 * 本文件在 clang 层面完全合法（编译通过）——C 的强制转换随便写，寄存器类型的
 *   核对发生在加载期。本对为 tracepoint 程序类型（无 XDP 挂载风险），画廊骨架中
 *   的 uapi 常量块按 C2 说明不加。修复形态见同目录 fixed.bpf.c——probe 系 helper
 *   受控读取；卡片讲解见本目录 README.md。
 */
#include "vmlinux.h"
#include <bpf/bpf_helpers.h>

SEC("tracepoint/syscalls/sys_enter_openat")
int probe_bad(struct trace_event_raw_sys_enter *ctx)
{
    char *fn = (char *)ctx->args[1];   /* 预期被拒：ctx 标量字段强转指针后直接解引用 */
    if (fn[0] == '/')                  /* 任意内核/用户地址必须走 probe 系 helper（第 2 章预告） */
        return 1;
    return 0;
}

char LICENSE[] SEC("license") = "GPL";
```

预期 verifier 日志关键行（预期输出示例 / 运行级待验证；日志行随内核版本略有差异）：

```text
R1 invalid mem access 'scalar'
```

关键行指认「对一个标量（scalar）类型的寄存器做了内存访问」，等价形态亦可作无前缀的 `invalid mem access 'scalar'`；寄存器号随产物而异（本对 bad 产物实测：解引用目标寄存器为 R1），指认点就是 `fn[0]` 那条字节读取指令，日志前文会给出该寄存器当前的类型与取值域。

为什么拒绝：2.3 类型表第一行——`SCALAR_VALUE` 是「纯数值，不指向任何内存」，**不可解引用**。分两步看：`ctx->args[1]` 这一步完全合法——ctx 本身是 `PTR_TO_CTX`，字段按申报布局访问，加载期静态放行（2.3 的上下文申报机制）；但从 ctx 加载出来的值在类型系统里只是标量——「一个数」。C 的强制转换能骗过编译器，骗不过验证器：类型随数据流走，寄存器没被登记为指针，解引用就没有任何「访问安全」的证明可言。放行意味着什么：程序可以把**任意 64 位数**当成地址去读——一次 `fn[0]` 就是一次不受界限检查的任意读。真正的任意地址必须走 probe 系辅助函数（2.7 的能力登记面）：helper 在内部把源地址限定在对应空间、按缓冲区大小受控拷贝，越界或缺页返回错误值而非崩溃。

fixed 修复片段（下贴 `book/examples/chapter-03/02-fail-gallery/07-kernel-ptr/fixed.bpf.c` 的 `probe_fixed` 函数；SEC 与返回值语义与 bad 一致）：

```c
SEC("tracepoint/syscalls/sys_enter_openat")
int probe_fixed(struct trace_event_raw_sys_enter *ctx)
{
    char fn[64] = {};                  /* 修复：probe 系 helper 受控读取到栈缓冲 */
    long n = bpf_probe_read_user_str(fn, sizeof(fn), (const void *)ctx->args[1]);
    if (n > 0 && fn[0] == '/')         /* 5.5+ 用 user 变体；旧版 bpf_probe_read_str 行为随架构，保守注明 */
        return 1;
    return 0;
}
```

版本演进点（保守注明）：`bpf_probe_read_user_str` 为 5.5+（probe 系按访问空间拆分）；更旧内核的 `bpf_probe_read_str` 读取空间随架构配置而异，以所用内核文档为准。

修复原则一句话：**任意内核/用户地址一律走 probe 系辅助函数读入栈缓冲**（`bpf_probe_read_user_str` / `bpf_probe_read_kernel*`），判读放在「读取成功」分支内；绝不解引用「来源不是验证器登记的指针类型」的任何值——map value 里存的地址、报文里读出的指针值同理。

**教师视角**：本节的编排是「先见尸体、再学解剖」——七对按「从最常见到最隐蔽」排列：判空（3.1）与报文边界（3.2）是初学者第一周就会撞上的两类；指针算术（3.3）与栈初始化（3.4）开始要求理解类型系统与路径跟踪；循环（3.5）、白名单（3.6）与任意地址（3.7）要懂验证器的信任模型才看得懂「拒绝的理由」。顺序与一、二节相反：先看现场再回头读原理，是因为拒绝日志本身就是最好的「为什么」引子——但若只有现场没有一、二节，读者只会把七条日志背成七条咒语。读者最容易卡住的地方：把「被拒」当编译错误排查——反复检查语法、换编译器、怀疑环境，而日志指认的是具体指令；正确动作永远是读日志、把信号对回根因类别（四节实战专教这件事）。最后一个提醒：3.3/3.4/3.5 三对 bad 里的防折叠写法（消费比较、volatile、XOR 累加）是编译级可观测性装置、不是修复模式——它们是为了让肇事指令在产物里存活而做的技术处理，别学成「写 BPF 要加 volatile」。

**学生动手**：按画廊总览 README 的三步逐对走读（01→07）：进入每对目录，先 `make`——bad 与 fixed 都要编译成功（bad 的验收口径就是编译成功）；再 `diff bad.bpf.c fixed.bpf.c`，亲眼确认只差一处语义；然后把本节七个 card 的预期 verifier 日志关键行抄进自己的笔记，与 diff 的差异行一一对号——「哪一行的删除/新增对应哪条日志」。拿到特权环境时逐个加载 bad 观察真实日志（运行级待验证——编写环境无加载权限），与笔记里的预期行对照。做完七对，回到 1.4 学生动手写下的问题清单对答案。

检查点（先自答，再看提示）：

## 四、实战：读懂你的第一条 verifier 日志

一至三节回答了「验证器是什么、怎么验、拒绝长什么样」，本节把镜头换到你手上：在本章自己的示例上走完「编译 → 加载 → 观察 → 读日志」的闭环。观察走锚点 `01-pkt-parse` 的通过路径，读日志走画廊 02 的被拒路径——XDP（eXpress Data Path，快速数据路径）锚点与画廊 02 的 bad 互为镜像，后者就是前者删掉全部界检查的形态。5.1 按五层把环境备齐（层序与第 2 章 5.1 一致，场景收窄为「加载即部署」的 XDP 单机验证）；5.2 走读两条路径的代码，把三节两次预告的「把『信号 → 根因类别』映射变成排错工作流」兑现成可操作的三步流程。

### 5.1 五层环境（紧凑版）

#### 第一层：依赖环境

**内核版本与 BTF**：示例要求 Linux 5.10+ 且开启 `CONFIG_DEBUG_INFO_BTF`——XDP 程序类型、`bpf_program__attach_xdp`（本机 libbpf 1.3 头文件已含）与 skeleton 工作流在 5.10 上均已可用；`make` 第一步由 bpftool 从 `/sys/kernel/btf/vmlinux` 生成 `vmlinux.h`，BTF 缺失则编译停在第一步（自建带 BTF 内核的路径见附录 C）。本机内核 7.0，在基线之上。

**权限矩阵**。加载 BPF 程序需要特权（1.3 加载路径的档位判别——`-EPERM` 的来源）；与第 2 章 tracepoint 权限档的关键差异在挂载一列：tracepoint 挂载是纯观测，不需要 `CAP_NET_ADMIN`；XDP 挂载要接管接口的收包路径，**必须 `CAP_NET_ADMIN`**（第 17 章 TC 同此要求）：

| 环境档位 | 可编译 | 可加载 | 可挂载 XDP |
|---|---|---|---|
| root | 可 | 可 | 可 |
| 非 root + `CAP_BPF`+`CAP_NET_ADMIN` | 可 | 可 | 可 |
| 非 root 且无上述能力 | 可 | 不可 | 不可 |

组合要求随内核版本略有差异，教学上以 root 或第二档为稳妥口径。本机真实档位是第三行：非 root、`/proc/sys/kernel/unprivileged_bpf_disabled` 实测为 2——编译全可、加载不可，这正是 5.2 全部输出标注「运行级待验证」的原因。

**工具清单与检查方法**：清单不必背——运行 `bash book/examples/chapter-03/00-env/check-env.sh`（无 root 也可），脚本按「内核与 BTF → 工具链（编译级）→ 权限分级（加载级/运行级）」三段输出并给出三档结论。本机第三段输出（本地验证）：

```text
== 权限分级（加载级/运行级） ==
OK    具备 CAP_BPF：可加载程序，挂载 XDP 还需 CAP_NET_ADMIN
OK    lo 接口存在（XDP 锚点程序的推荐挂载目标）

结论：编译级依赖齐备；加载级/运行级能力见上方权限分级输出。
```

三档结论的读法：前两段（内核与 BTF、工具链）全 OK，编译级成立——5.2 动手清单全部可完成；lo 存在，运行级的挂载目标在。那行 OK 要按第 2 章 5.1 拆过的同名偏差读：脚本检的是 capsh 的 bounding set（能力边界集），本机 bounding set 恰含 `cap_bpf`，但 bounding set 不等于生效能力（`capsh --has-p=cap_bpf` 实测 not permitted，本地验证）——真实档位仍是上表第三行，加载级结论以「非 root、`unprivileged_bpf_disabled=2`」为准。

#### 第二层：编译环境


#### 第三层：部署环境

**「加载即部署」是本章与第 2 章场景的根本差异**：第 2 章 tracepoint 的部署是往运行中的内核挂一个观测点；本章 XDP 程序的验证、JIT 与挂载压缩进同一次加载调用——`bpf(BPF_PROG_LOAD)` 返回的一瞬间，安全性裁决已经完成（1.3 的四步路径）。于是本章没有独立的「部署验证」步骤：`bpftool prog load` 与锚点 loader 的 `open_and_load`（`pkt_parse.c`）都是验证现场——命令返回成功即验证通过，返回 `-EACCES` 即验证拒绝、日志同步到手（拿到手的方法见 5.2 被拒路径）。

部署动作只剩选挂载目标：XDP 挂到网络接口上，本章只用 `lo`（回环接口）或自建的 veth（virtual Ethernet，虚拟以太网接口对）。安全警告（本章示例统一措辞）：

> XDP 程序直接作用于网卡收包路径——本章示例只应挂在 veth 或 lo 上实验；切勿在不了解影响前挂到生产物理网卡。

与第 17 章「勿挂物理网卡」红线（「绝不要挂到物理网卡或 SSH 正在使用的接口」）的呼应：两条措辞是同一条纪律的两种口径——那里的防火墙程序本来就要丢包改包，失联风险连着带外恢复预案一起写；本章程序只观测不干预，风险面更小，但挂载动作发生在驱动收包路径上，挂错接口影响的仍是全系统网络，「不了解影响前不挂生产物理网卡」没有豁免。

#### 第四层：运行环境

启动与停止共两条：`sudo ./pkt_parse lo` 前台运行，Ctrl-C 退出即卸载（`bpf_link__destroy` 加 `__destroy`，引用归零、对象回收——第 2 章 4.4 的同一条链）。两句「没有」：没有规则下发——锚点无控制面语义，loader 本身就是全部控制面；没有 pin——map/prog/link 的存活完全跟随进程（第 2 章 4.5「不 pin」的一侧）。挂载模式一句话（README 与正文统一措辞）：flags=0 挂载时若驱动不支持原生 XDP，内核一般会自动回退到 generic（SKB）模式——具体行为随内核版本，以实测为准（回退的含义：原生模式在驱动层收包，generic 模式退到协议栈入口按 SKB——套接字缓冲，内核报文的标准载体——逐包处理，功能等价、性能路径不同）。

### 5.2 代码走读：通过与被拒两条路径

**教师视角**：为什么用「同一类检查的正反两面」教学？三节画廊是七个不同根因的横截面，本节做一次纵剖——画廊 02 的 bad 就是锚点删掉全部界检查后的形态（这份亲缘关系写在 bad 的头注释里）。同一解析链「每层一行检查」与「一行都没有」并排放着，边界检查就从「要背的规则」变成「能 diff 的因果」。读者容易卡住的两处先亮出来：其一，「预期日志哪里来的」——编写环境无加载权限，日志不能本机实测，口径是教学推导：以 5.10+ 稳定措辞与 `Documentation/bpf/verifier.rst` 为基准给出关键行，全部标注「预期输出示例 / 运行级待验证」，你拿到特权环境后用真实日志对账即可；其二，「日志第一行该看什么」——答案恰恰是别从第一行读起：2.7 讲过日志逐指令展开、每行是「指令号 + 执行后的寄存器状态」，动辄上百行，**结论在最后一行**，读法是先读尾行、再向上回溯肇事指令。

先读**通过路径**。下贴 `book/examples/chapter-03/01-pkt-parse/pkt_parse.bpf.c` 第 25–57 行（程序本体；文件头注释、include、map 定义与末行 license 见源文件——头注释一句话点题：缺一层界检查就会被拒，现场见画廊 02）：

```c
SEC("xdp")
int pkt_parse(struct xdp_md *ctx)
{
    /* xdp_md 的 data/data_end 是寄存器宽度裸指针，经 (long) 中转标准转换 */
    void *data = (void *)(long)ctx->data;
    void *data_end = (void *)(long)ctx->data_end;

    /* 第一层：以太网头——解引用前先证明 [data, data+14) 在报文内 */
    struct ethhdr *eth = data;
    if ((void *)(eth + 1) > data_end)
        return XDP_PASS;                       /* 截断报文：放行交协议栈处理 */
    if (eth->h_proto != bpf_htons(ETH_P_IP))   /* h_proto 为网络字节序 */
        return XDP_PASS;

    /* 第二层：IPv4 头——边界检查以「上一层尾=这一层头」推进 */
    struct iphdr *ip = data + sizeof(*eth);
    if ((void *)(ip + 1) > data_end)
        return XDP_PASS;
    if (ip->protocol != IPPROTO_UDP)
        return XDP_PASS;

    /* 第三层：UDP 头——同一模式再走一遍；不读 payload，无需更深的检查 */
    struct udphdr *udp = (void *)ip + sizeof(*ip);
    if ((void *)(udp + 1) > data_end)
        return XDP_PASS;

    __u32 key = 0;
    __u64 *count = bpf_map_lookup_elem(&udp_counts, &key);
    if (count)                                  /* array map 单槽恒在，防御式检查 */
        __sync_fetch_and_add(count, 1);         /* 原子递增：多网卡队列并发安全 */

    return XDP_PASS;                            /* 只观测不干预，一律放行 */
}
```

逐段看验证器看到的世界。开头两句把 `ctx->data`/`ctx->data_end` 装进两个指针——此刻它们是「毫无关系的指针」（2.5 的原话），任何访存的安全性都还没被证明。三层检查是本章的题眼，**推进模式**：第一层 `if ((void *)(eth + 1) > data_end)` 证明整个以太网头（14 字节）落在报文内——比较在「不返回」的路径上建立了报文指针与尾界的相对关系（2.5），此后的 `eth->h_proto` 读取才可证明；第二层指针取 `data + sizeof(*eth)`——上一层尾 = 这一层头，再比一次，`ip->protocol` 的读取随之可证明；第三层把同一模式再走一遍。三行检查的分工要看准：前两层各保一次真实的字段读，第三层检查之后并没有 `udp` 的字段读取——它是推进模式的示范位：哪天要读 UDP 头字段，检查已经就位；反过来删掉它，程序预期仍能通过验证（检查是为解引用服务的——检查点第 1 问专门拆这件事）。字节序一处：`eth->h_proto` 是网络字节序，比较前过 `bpf_htons(ETH_P_IP)`；漏转换编译期合法、运行期行为错——验证器不管语义对错（1.4 的「安全不含逻辑正确」）。收尾三件事：`bpf_map_lookup_elem` 拿计数槽，`if (count)` 是防御式判空（array 单槽恒在，非 verifier 硬性要求——1.2 的调停口径）；`__sync_fetch_and_add` 原子递增消除多网卡队列的写竞争（验证器对原子操作天然放行，第 2 章 3.4 竞争样本的对策面）；出口一律 `XDP_PASS`——解析、计数、放行，只观测不干预。

再读**被拒路径**。下贴 `book/examples/chapter-03/02-fail-gallery/02-pkt-bounds/bad.bpf.c` 全文（3.2 按画廊格式讲过它的「为什么被拒」，这里换「日志怎么读」的视角）：

```c
// SPDX-License-Identifier: GPL-2.0 OR BSD-3-Clause
/*
 * 画廊 02-pkt-bounds / bad：预期被拒：报文边界检查缺失——首个越界读在 eth->h_proto。
 *
 * verifier 为什么会拒绝：packet 指针（从 ctx->data 起）指向长度可变的报文，网络
 *   报文随时可能被硬件/上游截断，验证器（verifier）无法凭「一般报文够长」放行——
 *   每个字段的读偏移都必须先与 data_end 界标比较、证明落在报文内。本程序把
 *   eth/ip 两层指针推进后未做任何 (void *)(指针 + 1) > data_end 检查就读字段，
 *   第一个字段读 eth->h_proto（偏移 12..13）时已不可证明在报文内——越界读会泄出
 *   报文缓冲区之外的内核内存，因此加载期直接拒绝。
 *
 * 对照通过路径锚点 ../../01-pkt-parse/pkt_parse.bpf.c：同一解析链，每层解引用前
 * 先做界检查即放行。本文件在 clang 层面完全合法（编译通过）；修复形态见同目录
 * fixed.bpf.c——仅插入两层界检查；卡片讲解见本目录 README.md。
 */
#include "vmlinux.h"
#include <bpf/bpf_helpers.h>
#include <bpf/bpf_endian.h>    /* bpf_htons：h_proto 为网络字节序 */

/* uapi 常量不在 vmlinux.h 中（BTF 只含类型），画廊 XDP 类骨架统一手工定义 */
#define ETH_P_IP 0x0800
#define IPPROTO_UDP 17

SEC("xdp")
int probe_bad(struct xdp_md *ctx)
{
    void *data = (void *)(long)ctx->data;
    void *data_end = (void *)(long)ctx->data_end;
    struct ethhdr *eth = data;
    struct iphdr *ip = data + sizeof(*eth);
    if (eth->h_proto == bpf_htons(ETH_P_IP) && ip->protocol == IPPROTO_UDP)
        return XDP_DROP;           /* 预期被拒：首个越界读在 eth->h_proto（无任何 data_end 检查） */
    return XDP_PASS;
}

char LICENSE[] SEC("license") = "GPL";
```

预期 verifier 日志关键行（预期输出示例 / 运行级待验证；日志行随内核版本略有差异）：

```text
R2 offset is outside of the packet
```

逐行读法按三步走——这套步骤就是本章要教的排错工作流（三节末检查点预告的兑现）：

- **第一步：分清失败在哪一层**。真实加载时 libbpf 把完整日志打到 stderr（log_buf 机制，2.7）；用 `bpftool prog load` 直接加载产物则日志跟在命令输出后，详细度由 log_level 档位控制（细目收在排错节）。拿到日志先确认它是验证拒绝（`-EACCES`）而非权限失败（`-EPERM`）——两者判别见 1.3，混着查最浪费时间。
- **第二步：读尾行认信号**。`R2 offset is outside of the packet` 指认「寄存器 R2 的偏移已超出报文范围」（部分版本作等价措辞 `invalid packet access`），肇事指令就是日志倒数几行里那条 `eth->h_proto` 的读取——错误结论在最后，原因在它前面的指令轨迹里。`R2` 是**被拒访存的基址报文指针**，源码里就是 `eth`；但别把编号当知识——寄存器随 clang 的分配变化，本机 clang 18 对这份源码的产物里 `eth` 实际落在 r1（`llvm-objdump -d bad.bpf.o` 可自查：`r2 = *(u16 *)(r1 + 0xc)`，r2 是读入值的寄存器、被指认的基址是 r1）——3.2 的「认措辞与偏移语义，别认编号」在此实操化。日志里的出处要分清：`off=`（相对报文起点的偏移）出现在寄存器状态行，访问宽度出自肇事指令行本身——如 `r2 = *(u16 *)(r1 + 0xc)` 的 `u16`。挂回源码，`eth->h_proto` 就是偏移 12、宽 2 字节——验证器在说「在 off 12 读 2 字节，是否落在报文内不可证明」。
- **第三步：信号对根因，根因改源码**。`offset is outside of the packet` 属报文边界类——根因是「推进指针后没有与 `data_end` 的比较」，对策是补回界检查（同目录 fixed 的两层检查即最小修复，修复原则见 3.2）。日志文本随内核版本漂移，「措辞 → 根因类别」的映射与这三步流程不漂移——排错节把它们收成速查表。

## 可视化：验证器状态探索与剪枝

二节 2.4 的「两条路各模拟一遍、等价即剪」与一节 1.3／二节 2.1 的加载路径，各用一张 text 图收拢如下。两图均为示意：寄存器编号与取值域随内核版本与编译产物漂移，状态行口径同「预期输出示例 / 运行级待验证」（约定沿三节）。

**图 1：双分支程序的状态探索树**。演示程序是画廊 01 与 04 同款的判空骨架（教学构造，非画廊文件；映射取锚点的 `udp_counts`）：lookup 之后判空，用声明即初始化的 `verdict` 记录命中与否——`__u64 verdict = 0; if (v) verdict = *v; if (verdict > 10) return XDP_DROP; return XDP_PASS;`。

```text
入口：ctx 定型为 PTR_TO_CTX；key = 0
  │ bpf_map_lookup_elem(&udp_counts, &key)
  ▼
v = map_value_or_null            ←联合定型「值或 NULL」（2.3）
  ├─ 臂 1（v 非空；先探索的顺序路径）
  │    v 收窄为 map_value；verdict = *v → 取值域 [0, 2^64−1]
  │      ▼
  │    汇合点 J：if (verdict > 10)  【首次到达，记录状态 S】
  │      ├─ 为真：XDP_DROP 出口（叶子）
  │      └─ 为假：XDP_PASS 出口（叶子）
  └─ 臂 2（v == NULL；连同状态压入待探索栈，臂 1 走完才弹出——2.4）
       v 为标量 0；verdict 保持声明初值 → 取值域 [0,0]
         ▼
       汇合点 J：第二次到达——与 S 逐项比对（regsafe 一族，2.4）
         verdict 的 [0,0] 不宽于 S 的 [0, 2^64−1]，其余待读寄存器一致
         ⇒ 剪枝标记：J 往后的探索已被臂 1 覆盖，整段跳过
```

怎么读图 1：每个节点是一条待探索路径，节点里写着此刻的寄存器状态。验证器深度优先：先沿臂 1 走到底，两片叶子都探索完；臂 2 连同状态躺在待探索栈里（`push_stack` 一类函数，2.4），臂 1 走完才弹出继续。两条臂在同一条指令 J 重逢、各带各的状态——这是剪枝登场的前提。

剪枝判定就发生在 J 的第二次到达：把新状态与首次记录的 S 逐寄存器比对（`regsafe` 一族，2.4），**新状态不比 S 更宽**才算等价——本例 `verdict` 的 [0,0] 是 [0, 2^64−1] 的子集。比对只针对后续仍会被读取的寄存器（活跃性（liveness）机制，随内核版本演进，以所用内核源码为准）——`v` 在 J 之后无人再读，其类型差异不阻碍剪枝。于是臂 2 从 J 往后整段免验，探索步数省一半；分支一多，等价重逢把指数增长的路径数压回可控规模——2.4「状态爆炸为什么没有发生」的图形版。

两个补充：等价口径过宽会剪掉真错误，验证器在边界推导依赖精确值时临时收紧比对口径（精度追踪，2.4）；换成锚点的字节序判断，机制不变、树的形状变——`if (eth->h_proto != bpf_htons(ETH_P_IP))` 同样分出两条路，但「非 IPv4」臂直接出口、两臂不重逢，锚点里因此看不到剪枝。剪枝只在两条路于同一条指令重逢时登场；2.4 说过 Linux 实现没有显式合并点，剪枝标记就是「汇合点保守合并」在实现里的家。

**图 2：加载-验证双结局流程**（与 1.3 的四步、2.1 的管线同口径）：

```text
用户态 loader                           内核（bpf() 入口，kernel/bpf/syscall.c）
──────────                             ──────────────────────────────────────
bpf(BPF_PROG_LOAD) ──────────────────► ① 属性与 license 检查（1.3）
                                         │ license 不兼容 ──► 拒绝：-EACCES + 日志（log_buf）
                                         ▼
                                       ② verifier 静态验证（bpf_check()，2.1）
                                          ├─ 预处理：重定位一类（map fd 解析）
                                          ├─ CFG 检查：跳转落点、回边裁决（2.6）
                                          ├─ 逐指令探索主循环（2.2–2.5）
                                          │    状态推演 → 分支压栈 → 剪枝 → 访存裁决
                                          │    （图 1 就是这个循环的内部视角）
                                          └─ 收尾修正：死代码清除等（2.1）
                                         │ 任一步不可证明 ──► 拒绝：-EACCES + 日志
                                         ▼
                                       ③ JIT 编译为本机指令（第 6 章）
                                       ④ 组装程序对象，返回 prog fd
attach 挂载（第 2 章 4.4）────────────► 挂载点生效，事件触发程序执行
```

怎么读图 2：左列是 loader 的动作，右列是同一次系统调用在内核里的内部次序，①–④与 1.3 的四步一一对应；②的内部就是 2.1 的管线，探索主循环一格是图 1 在整体中的位置——两图互为内外景。

两个结局的分叉点不止一处：license 不兼容、CFG 检查、探索主循环、收尾修正，任一步「不可证明」都以同一形态退场——`bpf(BPF_PROG_LOAD)` 返回 `-EACCES`，日志经 log_buf 带回用户态（1.3）。这是 5.1「加载即部署」的图形版：返回成功的一瞬间三类保证已兑现，返回失败的一瞬间逐指令轨迹已到手（怎么拿见排错节第②组）。入口之前还有一道权限档位——不足即 `-EPERM`、程序没进验证，判别流程见排错节第③组。通过路径收尾：③JIT 译成本机指令（第 6 章），④返回 fd——程序还没挂在任何事件上，attach 挂载是下一道门（XDP 需 `CAP_NET_ADMIN`，5.1 权限矩阵）；「验证一次付费、数据面零开销」（1.2）在图上就是②与末行的距离。

## 常见问题与排错

四节 5.2 的三步工作流教你「读」一条日志，本节把它收成「查」的四组表。口径沿全章：日志行均为预期输出示例 / 运行级待验证，随内核版本略有差异（三节统一口径）；查表认「信号 → 根因类别」的映射，不背文本（2.7 教师视角）。

**第一组：verifier 日志信号速查表**——七类画廊拒绝（3.1–3.7）加练习 2 的负偏移信号，共八行：

| 日志信号（关键行） | 根因类别 | 修复方向 | 现场 |
|---|---|---|---|
| `invalid mem access 'map_value_or_null'` | 查找返回值未判空即解引用（2.3） | 解引用前补判空收窄：`if (!v) return ...;` | [`02-fail-gallery/01-map-null/`](../examples/chapter-03/02-fail-gallery/01-map-null/) |
| `R2 offset is outside of the packet`（或 `invalid packet access`） | 报文指针推进后没有与 `data_end` 的比较（2.5） | 每层解引用前补 `(void *)(指针 + 1) > data_end` 界检查 | [`02-fail-gallery/02-pkt-bounds/`](../examples/chapter-03/02-fail-gallery/02-pkt-bounds/) |
| `R2 pointer arithmetic on pkt_end PROHIBITED` | 对报文尾界指针本身做算术（2.3） | 算术移到 packet 指针上，`data_end` 全程只作比较 | [`02-fail-gallery/03-ptr-math/`](../examples/chapter-03/02-fail-gallery/03-ptr-math/) |
| `R2 !read_ok`／`invalid read from stack off ... size ...`（两种真实形态，无拼接体） | 分支外读未初始化栈槽（2.6）；特权加载（`CAP_PERFMON` 一类档位）放行该读——「预期被拒」仅在允许非特权 BPF 的配置成立 | 声明即初始化，读之前每条路径都写过 | [`02-fail-gallery/04-stack-uninit/`](../examples/chapter-03/02-fail-gallery/04-stack-uninit/) |
| `infinite loop detected at insn ...`（特权路径主形态）／`back-edge from insn ... to ...`（非特权路径形态） | 循环上界不可证明，状态探索不收敛（2.6） | 上界先掩码收窄（`n & 0xF` 一类）再进循环；或改用 `bpf_loop`（5.17+） | [`02-fail-gallery/05-loop/`](../examples/chapter-03/02-fail-gallery/05-loop/) |
| `unknown func bpf_get_current_pid_tgid#14`（一般形态：`unknown func <名>#<id>`） | 辅助函数不在本程序类型白名单——「查无此函数」，不是「禁止使用」（2.7） | 查适用面（uapi 头注释或 `bpftool feature probe`），换白名单内等价能力 | [`02-fail-gallery/06-helper-misuse/`](../examples/chapter-03/02-fail-gallery/06-helper-misuse/) |
| `invalid mem access 'scalar'`（可带寄存器前缀，如 `R1 invalid mem access 'scalar'`） | 标量值被当指针解引用（2.3） | 任意地址一律走 probe 系辅助函数读入栈缓冲 | [`02-fail-gallery/07-kernel-ptr/`](../examples/chapter-03/02-fail-gallery/07-kernel-ptr/) |
| `R2 min value is negative, either use unsigned or 'var &= const'` | 可能为负的值被当偏移加到指针上——有符号/无符号两套界混用（2.5） | 改用无符号语义对齐两套界，或掩码收窄到非负 | [`exercises/02-log-diagnosis/`](../examples/chapter-03/exercises/02-log-diagnosis/) |

**第二组：日志获取与详细度**——2.7 的机制（`verbose()`、log_level 档位）落到手上：

| 现象／需求 | 原因与处理 |
|---|---|
| loader 侧想自己接管日志，而不是看 stderr | libbpf 默认把验证日志打到 stderr；要重定向进自己的代码，注册日志回调（`libbpf_set_print()` 一族——名称与签名随 libbpf 版本演进，1.0 之前的旧版还伴随 `libbpf_set_strict_mode()` 一类严格模式开关，以所用版本文档为准） |
| `bpftool prog load` 报失败但看不到逐指令过程 | bpftool 失败时会输出验证日志；要看更完整的轨迹加 `-d`（`--debug`）——选项与默认详细度随 bpftool 版本略有差异，以 `bpftool prog help` 为准 |
| 日志只剩半截、最后一行结论缺失 | 缓冲区过小导致截断（2.7）：loader 侧调大 log_buf，或先调低 log_level 只拿结论、确认根因后再逐步调高复现 |
| 逐指令轨迹上百行，读不动 | 2.7 预告的 log_level 细目在此收口：0 只给结论、1 逐指令轨迹、2 追加更细状态（语义随内核版本略有差异）——先 0 认信号，再 1 回溯肇事指令（5.2 工作流的档位选择） |

**第三组：权限类失败区分**。第 2 章排错节把 verifier 日志精读「指向第 3 章」的那次指向，在本组与第①组兑现（预告⑧收口）。判别流程一句话：拿到加载失败先只答一个问题——**进没进验证？** `-EPERM` 没进（查权限档位），`-EACCES` 已进（读验证日志）；混着查最浪费时间（1.3）。

| 现象 | 原因与处理 |
|---|---|
| 返回 `-EPERM` | 程序没进验证就被权限档位挡住（1.3）：非 root 且 `unprivileged_bpf_disabled=2`，或缺 `CAP_BPF` 一类能力。以 root 或特权档运行；无特权环境退回编译级自查（`make` 加 `diff`，见 5.1 权限矩阵第三行） |
| 已 root 仍 `-EPERM` | 5.11 前的内核按 `RLIMIT_MEMLOCK` 计费，程序与映射过大撞上限——第 2 章排错节第一组已析，此处不重复 |
| 返回 `-EACCES`，日志含指令与寄存器状态 | verifier 拒绝：按第①组速查表把尾行信号对回根因，走 5.2 三步工作流 |
| 返回 `-EACCES`，日志不含指令轨迹 | 属性检查层的拒绝（1.3 第 1 步）：最常见是 license 不兼容——核对 `char LICENSE[] SEC("license")` 声明与所调辅助函数的 GPL 要求（2.7） |

**第四组：版本差异导致的拒绝差异**。同一份字节码，换个内核可能「能过」与「被拒」互换——本章三个版本演进点的对照：

| 特性 | 演进节点 | 对拒绝行为的影响 | 本章位置 |
|---|---|---|---|
| 有界循环 | 5.3 | 之前：回边一律拒绝（`back-edge` 形态）；起：特权程序放行，终止性改由状态探索收敛裁决（`infinite loop` 成为特权路径主形态） | 2.6／画廊 05 |
| `bpf_probe_read_user_str` | 5.5 | 之前：无 user/kernel 变体拆分（`bpf_probe_read_str` 读取空间随架构）；不足 5.5 调用 user 变体，落进白名单 miss 的 `unknown func` 一族 | 3.7 |
| `bpf_loop` | 5.17 | 之前：不可用；起：可把迭代交给内核辅助函数执行，是掩码定界之外的另一条出路 | 3.5／2.6 |

演进点不止这三处：白名单随版本增删，边界推导与剪枝口径随版本收紧或放宽，发行版默认配置各有取舍——同一份字节码在两个内核上一过一拒并不罕见。保守结论只有一句：**以所用内核的 `Documentation/bpf/verifier.rst` 与实测为准**（本机内核 7.0 仅作本章编译口径参考）。

## 总结

本章回答了第 2 章反复预告的那个问题：一段编译通过的字节码，凭什么能进内核。验证器的回答是三类保证——**内核态内存安全**：每一次访存可证明落在合法区域，靠的是给每个指针配上类型与边界的寄存器状态族（2.3；现场见 3.1/3.2/3.7）；**可终止**：跳转落在程序内、循环可证明收敛、指令预算兜底（2.4/2.6；现场见 3.5）；**权限最小化**：辅助函数白名单按程序类型正向登记，上下文按申报访问（2.7/2.3；现场见 3.6）。安全模型收成一句话：**静态证明 + 运行时定界**——加载期能证明的绝不留给运行时，证明不了的由辅助函数内部定界与显式边界检查兜底；「拒绝即安全」的代价是合法程序也可能被拒（1.4），这是换取数据面零检查开销的设计取舍，不是缺陷。机制、现场与工具各就其位：二节拆流水线，三节摆七类现场，四节给读日志的三步工作流，可视化与排错两节分别收成图与速查表。
